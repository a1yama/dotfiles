# CLAUDE.md
Research the codebase before editing. Never change code you haven't read.

## Conversation Guidelines

- 指示が曖昧だったり疑問があった場合にはそのまま作業に入らず質問をしてください。
- 明確な2〜4択をユーザーに問うときは、文章で聞かず `AskUserQuestion` ツールを使う(自由入力が要る場合は文章で聞く)。
  - 「次に何をするか」の候補提示も対象。候補を表や箇条書きで並べて「どれから進めますか」と本文で聞くのは禁止。候補を選択肢、各候補の補足を description に入れて `AskUserQuestion` で出す。
  - 5択以上になるなら、まず推奨する2〜4件に絞って `AskUserQuestion` を出す(残りは「その他」で受ける)。
  - `label` は折り返さない短さにする(全角25文字まで)。長い説明は `description` に回す。ラベルが複数行になるとキー入力を受け付けなくなることがある。
  - `preview` は使わない。見せたい差分やコード案は `AskUserQuestion` の前に本文で出しておく。
- **可逆な作業は「やりますか？」と確認せずそのまま実行する。** 対象: コード編集 / ファイル新規作成 / テスト・ビルド実行 / 調査・読み取り。「〜しましょうか？」「進めていいですか？」で止まらない。
  - 確認が必要なのは不可逆・外向きの操作のみ: commit / push / PR作成・更新 / ファイル・ブランチ削除 / 外部サービスへの送信・投稿。
  - その確認も本文で聞かず `AskUserQuestion` で出す(例: 「実行する」/「やめる」/「内容を見せて」)。
- **一度承認された方針・公開範囲・反映可否は、同一セッション内で再確認しない。** 前提が変わった場合のみ「何が変わったか」を添えて再確認する。
  - ユーザーが同じ指示を2回以上述べた場合、それは確定した決定として扱い、以降は確認せず実行する。
  - **例外: commit と push はこの対象外。毎回 `AskUserQuestion` で確認を取る。**
    過去に承認されたことを根拠に自動化しない。1セッションで十数回 push してしまった実例がある。
  - 確認するのは「異なる解釈で成果物が実質的に変わる場合」と「不可逆・外向きの操作」に限る。それ以外は判断して進め、結果報告時に前提を1行で明示する。
- 必要に応じてチームで対応してください。

## 最終報告の形

ターンの最後の応答は、**スクロールせずに「依頼がどうなったか」が分かる**構造にする。
適用するのはターン最後の応答のみで、ツール実行の合間の応答は対象外。

表示先はターミナル(tmux で分割していることが多い)を前提にする。
デスクトップアプリでも崩れないよう、**幅を仮定した書き方をしない**。

### テンプレート

行頭に絵文字ラベルを置き、節は空行で分ける。該当しない節は丸ごと省略する。順序は入れ替えない。

```
✅ **結論** (YYYY-MM-DD HH:MM)
<依頼に対する結果を1行・40字以内。手段ではなく成果>

🚧 **未達**
<依頼のうちやらなかった/やれなかったこと。無ければ節ごと省略>

🔧 **変更**
- `<ファイル名>` — <何をどう変えたか>

🧪 **検証**
- <実行したコマンド / ケース> → <結果>

⚠️ **未確認**
- <実機・目視・外部サービスなど検証しきれていないこと。無ければ「なし」>

💡 **補足**
<判断に効かない背景情報。任意>

▶️ **次の一手**
- あなた: <ユーザーが手を動かすこと。無ければ「操作不要」>
- こちら: <Claude が続けてやること。無ければ「待機」>
```

- **`結論` `検証` `次の一手` は省略しない。** 検証を実施していないなら「実施していない(理由)」と書く。
- **`結論` の行末に完了日時を付ける。** 最終応答を書く直前に `date '+%Y-%m-%d %H:%M'` を実行し、その実測値を使う。
  プロンプト投入時に注入される `現在日時` はターン開始時刻なので、長い作業では完了日時にならない。流用しない。
  日付が当日でも省略しない(ターンを跨いで読み返したとき何日の作業か分からなくなる)。
- `変更` はファイルを触ったときのみ。`未達` `補足` は該当時のみ。
- 質問に答えるだけのターンは `結論`(=答え) + 根拠 + `検証` + `次の一手` でよい。
- **節ラベルは見出しにしてもよい**(`### ✅ 結論`)。絵文字と見出しは併用してよい。
  - 節が4つ以上ある、または応答が1画面に収まらないときは見出しにする(スクロール中に現在地が分かる)。
  - 3節以下の短い報告は `✅ **結論** (日時)` のままでよい。見出しは縦に余白を取るので短い報告では冗長。
  - 見出しにする場合も日時は付ける(`### ✅ 結論 (2026-08-18 12:05)`)。
- 区切り線(`---`)は使わない。空行で足りる。

### 「次の一手」の書き方

読み終えたユーザーが**迷わず手を動かせる**ことだけが目的。状況説明はここに書かない。

- **動詞で書く。** 「PR #167 を開いて approve する」。❌「確認をお願いします」「ご検討ください」
- **今の一手だけ書く。** 将来の分岐を表で並べない。分岐が要るのは判断を求めるときだけで、そのときは `AskUserQuestion` を出す。
- **`あなた:` が空になるのを嫌がって作業を捏造しない。** 何もないなら「操作不要」と書き切る。
- **`こちら:` には実際に続ける作業だけ書く。** ターンが終わって止まるなら「待機」。バックグラウンド実行中なら何がいつ終わるかを添える。
- 判断を求めるなら、この節ではなく `AskUserQuestion` で選択肢にする。節に候補を並べて本文で「どれにしますか」と聞かない。
- **`あなた:` の中身が「次の指示を出す」だけなら、節に書かず `AskUserQuestion` を出す。**
  「A を進める、または別の指示を出す」は選択肢を節で誤魔化した形。候補を選択肢にして、自由入力は「その他」で受ける。
- **`こちら:` が待機なら、ユーザー側に必ず具体的な行動が入る。** 両方が受け身(「指示を出す」/「待機」)になっているときは、`AskUserQuestion` を出していないというだけ。

### 「待ち」があるときの書き方

**「結果が出たら確認します」で終わらせない。** それは何も決まっていないのと同じ。
待っているものがあるなら、次のどちらかに必ず振り分ける。

- **こちらが自動で続けられる** — 何を待ち、出たら**どこまで進めるか**を書く。ユーザーは `操作不要`。
  「完了を待って報告する」ではなく「完了を待って、基準クリアなら本番反映まで進める」。
- **人間の操作が要る** — **具体的な時刻**と、そのとき出す指示の文言を書く。
  「明朝」「終わったら」は時刻ではない。`07:30 頃に「結果を見て」と指示してください` と書く。
  所要時間が読めないなら「40分後(08:35頃)」のように見積もりを添える。

良い例:

```
▶️ **次の一手**
- あなた: 操作不要
- こちら: 再学習の完了(明朝 06:00 頃)を待って、基準クリアなら本番反映まで進める
```

```
▶️ **次の一手**
- あなた: 08:35 頃に「デプロイの結果を見て」と指示してください(CI が約40分)
- こちら: 待機。セッションを跨ぐので `.claude/notes/deploy.md` に手順を残した
```

❌ 悪い例:

```
▶️ **次の一手**
基準未満か大幅改善のときだけ相談させてください。   ← 状況説明。行動指示になっていない

- あなた: 「斤量の表示を進めて」または別の指示を出す  ← 選択肢なので AskUserQuestion にする
- こちら: 待機

- こちら: 結果が出たら確認します                    ← 確認して何をするのかが無い
```

### 検証に表を使う条件

表は幅を食うので、次を**全て**満たすときだけ使う。1つでも欠けたら箇条書きにする。

- 列が2つ(3列以上は tmux 分割時に折り返して崩れる)
- 行が3つ以上(2行以下は箇条書きの方が短い)
- 各セルが全角25文字以内

満たすとき(ケース名と結果が短く対になる):

| ケース | 結果 |
|---|---|
| 通常の Stop 通知 | pass |
| レジストリ未登録 | pass |
| 短ターン抑制 | pass |

満たさないとき(セルが長い、列が多い):

- 通常の Stop 通知 → pass
- レジストリに無いセッションのフォールバック表示 → pass

### 見やすさは装飾より中身

絵文字や太字は補助でしかない。読みやすさに効くのはこちら。

- **1文1行にする。** 80字を超える行は折り返して読みにくい。長い段落を書かない。
- **考えた過程を書かない。** 結果と根拠だけ残す。「〜しようと思ったが」は消す。
- **抽象語を具体に置き換える。** 「4ケース → 全て期待どおり」ではなく「通常/フォールバック/idle無通知/短ターン抑制 の4件 pass」。
- **長いパスはフルで1回だけ。** 以降はファイル名だけで指す。
- **縦を削る。** 該当しない節は省略し、同じことを2箇所に書かない。
- 1行目より前に前置き・挨拶・「承知しました」を書かない。
- `結論` の良い例: `✅ **結論** (2026-08-18 12:05)` / `Discord通知にセッション名・発端・所要時間を追加した`
  - ❌ `claude-notify を編集し、テスト送信して疎通を確認しました`(手段の話)
  - ❌ `完了しました`(何が完了したか分からない)
- **`検証` には実際に実行したものだけを書く。** 実行していないテストを書かない。
- 「動きます」「問題ありません」は、`検証` に対応する実行結果がある場合のみ書いてよい。
- `未確認` を空にしたいがために検証を省略しない。検証できないものは正直に `未確認` に残す。

## セッション運用

- 数時間以上に及ぶ作業では、区切りごとに決定事項・残作業・触ったファイルを `.claude/notes/<task>.md` に追記する(コンテキスト外の永続記録)。compact 後はこのファイルを読んで再開する。
- compact が発生したら、まず `.claude/notes/` と `git diff` で現状を再確認してから作業を続ける。要約の記憶だけで実装判断をしない。
- 長時間の作業では Stop フック `hooks/stop-frame-check.sh` が一定量のツール実行ごとに `frame-check` スキル(方針の監査)を要求する。要求されたら他より先に実行する。
- **他エージェントやユーザーからの提案を「記録」で終わらせない。** 受け取ったターンのうちに 実行 / タスク化 / 理由付きで棄却 のいずれかに落とす。「認識しました」だけで次の作業に戻らない。

## モデルの使い分け

**メインセッション(Opus)が実装を担い、Fable には「長く考えるほど質が上がる」判断だけを委譲する。**

| タスク | 担当 |
|---|---|
| コードの実装・編集・リファクタ・テスト作成 | メイン(Opus) |
| ビルド・テスト実行、レビュー指摘の反映 | メイン(Opus) |
| 方針が決まっている作業、1〜2ファイルで完結する調査 | メイン(Opus) |
| アーキテクチャ設計・技術選定・トレードオフ比較 | `design-fable` |
| 複数ディレクトリ/レイヤにまたがる横断調査 | `recon-fable` |
| 再現しづらいバグ・断続的な失敗の根本原因究明 | `rootcause-fable` |
| 長時間作業の方針・枠組みの監査 | `frame-check` スキル(`frame-review-fable`) |

Fable エージェントは書き込みツールを持たない。設計・調査・監査の結論だけを返し、実装はメインが行う。

### 委譲するときの作法

- **最初の1回で全部渡す。** 目的・背景・制約・完了条件・関連ファイルをまとめて書く。Fable は最初のターンに完全な仕様がある状態で最も性能が出るので、対話的に小出しにしない。
- **なぜそれが必要かを書く。** 「何をしてほしいか」だけでなく「その結果を何に使うか」を添える。
- **手順を細かく指示しない。** 前世代モデル向けの逐次手順を渡すと、かえって出力の質が落ちる。目的と制約を伝えて進め方は任せる。
- **1リクエストが数分かかる前提で組む。** バックグラウンドで走らせ、待つ間に依存しない作業を進める。

### 委譲しない基準

Fable は Opus の倍のコストがかかる。次のときは委譲せずメインで処理する。

- 既に方針が決まっており、判断ではなく作業が残っているだけ
- 探索範囲が特定済みで、Glob/Grep 数回で終わる
- 機械的な変換・一括置換・定型のリファクタ

## Coding Policy

### コメントのルール

- コードを読めば分かる内容のコメントは追加しない
- コメントは「何をしているか」ではなく「なぜそうしているか」を説明する

### テスト可能な設計

テストが書きにくいと感じたら、テストの書き方ではなく**実装の形**を変える。

- ビジネスロジックを副作用（ファイルI/O、プロセス起動、ネットワーク、時刻取得）から分離し、純粋関数に寄せる
- 副作用と環境依存は引数で渡す。関数内で `os.Getenv` / `process.platform` / `time.Now()` を直接呼ばない
- 分岐を生む条件（プラットフォーム、フラグ、現在時刻）は引数化し、テストから全分岐を踏めるようにする

テストケースは最低限この観点を埋める: 正常系 / 境界値 / 空・null・undefined / 不正入力 / エラー経路 / 再発防止（修正したバグごとに1本）。

### ツール選択ルール

以下の操作には専用ツールを使用する。**その専用ツールがセッションに存在する限り** Bash は最後の手段。

| 操作 | 使うべきツール | 使ってはいけないコマンド |
|---|---|---|
| ファイル検索 | Glob | ls, find |
| コンテンツ検索 | Grep | grep, rg |
| ファイル読み込み | Read | cat, head, tail |
| ファイル編集 | Edit | sed, awk |
| ファイル作成 | Write | echo >, cat <<EOF |

Bashを3回以上連続で使う場合、専用ツールで代替可能か・まとめられるか・スキル化すべきか自己チェックする。

このルールは PreToolUse フック `hooks/bash-tool-nudge.sh` が deny で強制する。
例外は次の3つだけで、いずれも「専用ツールでは実現できない」ことが条件。

- **専用ツールがそのセッションに存在しないなら Bash を使ってよい。**
  `Grep` / `Glob` が無効なセッションが実在する。一度そのツールを呼んで
  `No such tool available` エラーを確認すれば、以降フックは同種の Bash を自動で許可する
  (harness のエラーを transcript から読んで判定している)。無いツールを探し続けたり、
  毎回 `# tool-exception:` を書いたりしなくてよい。
- **代替不能なフラグは自動で許可される。** `tail -f` / `ls -l` `-t` `-S` /
  `find` の `-mtime` `-mmin` `-newer` `-size` `-exec` `-delete` など。
  更新時刻やサイズを見たいときは `ls -lt` を使う (Glob では取れない)。
- **それ以外は `# tool-exception: <理由>` をコマンドに添える。**
  理由を書けないなら例外ではない。同じセッションで何度も書いているなら、
  上2つのどちらかに当てはまっていないかを先に疑う。

## Git / PR Guidelines

- **勝手にコミットしないこと。push も同様に毎回確認する。**
  同一セッションで既に承認を得ていても、コミット/push のたびに `AskUserQuestion` を出す
- コミットメッセージは1行、**変更の目的**を記述、50文字以内目安
- Prefix（`feat:`, `fix:`, `refactor:` 等）を活用する
- 「Generated with Claude Code」「Co-Authored-By: Claude」は追加しない
- PRタイトルは70文字以内

## ハルシネーション防止

- **テストなしで「動きます」と言わない。** 新機能はUTを書いてパスしてから報告する
- **確認していないことは「確認していません」と言う。** 断定しない
- **外部リソースは実際に検証する。** URL等は推測で生成しない
- **仕様はドキュメントを確認してから実装する。** 記憶に頼らない
- **不可逆な操作は、意図しない実行が起きないことをテストで証明する**
