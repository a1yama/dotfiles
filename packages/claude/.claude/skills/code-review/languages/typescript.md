# TypeScript/JavaScript レビューチェックリスト

## よくあるミス

### 型安全性
- **`any` の多用**
  - 説明: 型安全性を失う原因となる。`unknown` や具体的な型を使うべき

- **型アサーション（`as`）の乱用**
  - 説明: 型の安全性を無視することになる。型ガードを使うべき

### 非同期処理
- **Promise の unhandled rejection**
  - 説明: async 関数の呼び出しで `.catch()` や try-catch が不足している

- **async/await の誤用**
  - 説明: 並列実行可能な処理を await で直列実行している

### null/undefined
- **null/undefined チェックの欠如**
  - 説明: Optional chaining（`?.`）や Nullish coalescing（`??`）を活用すべき

### バグ・ロジックエラー
- **「添字=レーン(節・声部・系列)」の配列状態を配列まるごとで持ち回すと、歯抜けの添字で状態が壊れる**
  - 説明: 歌詞の節・複数レーンのように「同じ要素が添字ごとに独立した状態を持つ」データで、直前の状態を `Map<groupKey, boolean[]>` のように配列ごと保存・上書きすると、ある要素がレーンAだけ値を持ちレーンBが空のときに、B の直前状態まで A の値で置き換わる。要素単位では正しく引き継いだように見えるので、全レーンが揃った入力のテストは必ず通り、歯抜け(節ごとにメリスマの長さが違う等)のときだけ壊れる。状態は `Map<`${groupKey}:${laneIndex}`, T>` のようにレーンまで含めた粒度で持ち、その要素が実際に値を持つレーンだけを更新する

- **未閉鎖の start/stop 区間を「今開いている集合」で検出すると、同じキーで上書きされた区間が漏れる**
  - 説明: `openByKey.set(key, span)` で「キーごとに1つだけ開ける」状態機械を書き、最後に `new Set(openByKey.values())` で未閉鎖を弾く実装は、stop が来ないまま次の start が来た場合に前の span がマップから消えるため検出できない。結果「終点がないので描画されない図形」が再生・集計にだけ影響する divergence になる。未閉鎖判定は区間オブジェクト自身に `closed` フラグを立てて `filter(s => s.closed)` で行い、マップからの消え方に依存させない

- **収束しない入力を無限ループガードだけで止めると、上限まで副作用が積み上がる**
  - 説明: 「1回で必ず1つ進む」前提の反復処理に `guard < limit` の上限を付けても、そもそも収束しない入力(単体で容量を超える要素を次のバケツへ送り続ける等)では上限回数ぶんの副作用(空要素の追加、無駄なコピー)が全部残る。ガードは異常時の停止用と割り切り、別途「今回の処理で状態が実質変化したか」「そもそも動かせない要素か」を見る判定を入れて打ち切る

- **forEach コールバック内の早期 return は continue であり、後段に足した処理ごとスキップされる**
  - 説明: `array.forEach(item => { if (...) return; ... })` の `return` はループ全体ではなく1要素の処理を打ち切る。既存コードが「対応する終端が見つからないので return」といったガードを複数持つコールバックに新しい描画・集計処理を追記すると、前段のガードに引っかかった要素では新処理も丸ごと飛ばされる。無関係な処理を並べる場合は `if (cond) { ... }` のブロック化に直すか、処理ごとに別ループへ分ける

- **「必ず1件以上返す」前提だった関数にフィルタを足して空を返しうるようにしたら、戻り値の長さをモード判定に使っている呼び出し元を洗い出す**
  - 説明: `collectSelectedEvents` のように、それまで「選択があれば必ず非空」だった関数に除外条件を追加すると、呼び出し元の `if (result.length > 0) { A } else { B }` が意図せず B(別モードのフォールバック)へ落ちる。B が破壊的操作(範囲外の一括クリア等)だと、絞り込みのつもりの修正がデータ損失に化ける。モード判定は「対象が選択されているか」など判定専用の述語で行い、内容の絞り込みと分離する

- **削除対象を「選択範囲の外」へ広げたら、削除後のカーソル/インデックス補正も同じぶんだけ追従させる**
  - 説明: 関連レコードの連鎖削除(親を消したら従属レコードも消す)を後から入れると、`filter` で落とす index 集合は正しく広がる一方、削除後の選択位置を `先頭選択index - 1` のような「選択範囲だけを前提にした式」で求めているコードが取り残されやすい。従属レコードが選択範囲より前にあるケースだけでカーソルが右へずれ、空になったコレクションで範囲外の index を指す。範囲外 index は多くの参照関数が `undefined` を返して黙って no-op になるため例外にならず、「削除直後にカーソルが見えない」「次の入力位置が1つずれる」といった間接的な症状として遅れて現れる。補正は「削除された index のうち基準 index より小さいものの個数」を数えて引き、削除後に要素数0なら `-1`(=先頭)へ落ちることをテストで固定する

- **start/stop 状態マシンを複数の分岐で処理するとき、状態の「読み」と「更新」の順序を分岐ごとに揃えないと端点の要素だけ挙動が食い違う**
  - 説明: オッターヴァ・ペダル・ダンパーのように「開始マーカーで状態を立て、終了マーカーの要素自身までは効かせ、その後に解除する」種類の状態は、`start を適用 → 状態を読んで要素に反映 → stop を適用` という3段の順序が意味を持つ。この処理を通常経路と特殊経路(装飾音符・不可視要素・別声部など)に分けて書くと、片方だけ `stop を適用 → 状態を読む` の順になり、終了マーカーを持つ要素だけが解除後の値で処理される(例: オッターヴァ終点の装飾音符だけ1オクターブずれる)。分岐が増えたら「状態の読みと更新の順序」を分岐間で突き合わせるか、順序を1つのヘルパーに閉じ込めて共有する

### React 固有
- **useEffect の依存配列の不備**
  - 説明: 依存する値が配列に含まれていない、または不要な値が含まれている

- **key prop の欠如**
  - 説明: リスト要素に一意な key が設定されていない

- **非同期イベントハンドラで await を挟んだ後に closure 由来の state で setState すると更新を取りこぼす**
  - 説明: async ハンドラ内で await(確認ダイアログ・fetch 等) を挟んでから、レンダー時に捕捉した state 変数を基に setState(newValue)(非関数型更新)すると、await 中に他の更新で変化した最新 state を上書きして変更を失う恐れがある。await をまたぐ更新は必ず関数型更新 setState(prev => ...) にするか、更新に必要な値を await 前に確定させる

- **コントロールド数値入力で「範囲外なら早期return」すると途中入力・クリアができなくなる**
  - 説明: input type=number の value を state 由来の値にバインドしつつ onChange で範囲外・空文字を早期 return して setState しないと、React が入力を元の値へ巻き戻すため、ユーザーが数字を1桁ずつ組み立てたり一旦クリアしたりできなくなる(スピナーのみ機能)。入力中は文字列をそのまま保持し、onBlur/Enter でクランプ確定するか、途中値・空文字を許容して確定時のみ検証する

- **条件付き disabled な要素への autoFocus はフォーカスが当たらずダイアログの Escape 閉じが壊れる**
  - 説明: モーダルの初期フォーカスを「状況により disabled になりうる先頭要素」に置くと、disabled 時にブラウザがフォーカスを付与せず、オーバーレイの onKeyDown にイベントがバブルしないため Escape での閉鎖が効かなくなる。初期フォーカスは常時有効な要素に置くか、オーバーレイ自体に tabIndex を付与する

### 描画・画像処理
- **画像をCanvas/PDF/imgへ貼るとき幅と高さに別々の縮尺を使うと縦横比が崩れる**
  - 説明: `addImage(url, 'PNG', x, y, W, H)` のような貼り込みで、Wを固定値(コンテナ幅)・Hを別の係数で算出すると、元画像の実寸(widthScale等で可変)と縮尺が食い違い、片方向だけ潰れて中身(音符・図形)が伸縮して見える。縦横比を保つには W・H に必ず同一のスケール係数を掛ける。貼り込み先の実際の描画幅(canvas.width/pixelRatio)から縮尺を決めるのが安全

- **描画ライブラリのグルーピングAPIに、そのAPIが受け付けない音価・型の要素を渡すと例外で描画全体が落ちる**
  - 説明: VexFlow の `Beam`(`GraceNoteGroup.beamNotes()` 経由)のように「複数要素をまとめて装飾する」APIには受理条件(例: 4分音符より短いこと)があり、違反すると `RuntimeError` を投げる。要素の生成側(エディタのコマンド)が新しく広い値域を許可した場合(例: 4分音符以上を装飾音符にできるようにした)、描画側のグルーピング呼び出しが暗黙に前提していた条件が破れ、その組み合わせでのみ描画関数全体が throw する。React では ErrorBoundary が無いとツリーごと落ちて画面が白くなり、データは正常・テストは緑のまま「特定の操作を2回したときだけ壊れる」形で現れる。しかも `Beam` は先頭要素の音価しか検査しないため、順序次第で例外にならず不正描画になるケースも混在する。生成側で値域を広げたら、その値を受け取る描画ライブラリAPIの受理条件を洗い出し、条件を満たす要素だけをグルーピングに渡す。テストは「新しく許可した値域 × 複数要素」の組み合わせで1本置く

- **当たり判定(ヒット領域)を新しい種類の要素へ広げたら、その領域を読む「選択以外」の経路も洗い出す**
  - 説明: クリック座標→要素の当たり判定配列(`regions.notes` 等)は、選択(`hitTest`)だけでなく「挿入位置の決定」「ドラッグ対象の特定」「ゴースト表示」など複数の経路から読まれることが多い。特殊要素(装飾音符・ゴースト・オーバーレイ)を新たに当たり判定へ登録すると、選択は意図どおり動く一方で、`insertAfterIndex = max(eventIndex where x_center <= click)` のような「index の最大値を取る」別経路が、これまで存在しなかった index を拾って挿入位置がずれる。ずれる範囲は数pxの帯なので手動確認では踏みにくく、例外も出ず、選択のテストは緑のまま「たまに要素が変な位置に入る」形で現れる。当たり判定配列に要素を足すときは、その配列を読む全関数を洗い出し、経路ごとに対象にすべきかを判断する(必要なら領域に種別フラグを持たせてフィルタする)

- **特殊要素を別経路で生成すると、共通ヘルパーが渡していた「座標系コンテキスト引数」が黙って既定値にフォールバックする**
  - 説明: VexFlow の `StaveNote`/`GraceNote` の `clef` や `staffLines` のように、見た目ではなく**座標系そのもの**を決める引数は、省略しても例外にならず既定値(`clef="treble"` 等)で描かれる。共通ヘルパー(`toStaveNote` 等)は必ず渡しているのに、装飾音符・全休符・ゴースト要素のような「特殊な描かれ方をするので別経路で `new` する」要素だけ渡し漏れやすい。結果は「例外なし・テスト緑・データ正常」で、ヘ音記号の段や5線以外の譜表という**既定値と一致しない条件を踏んだときだけ**要素が譜表外に浮く。既定条件で書いたテストは必ず通るため検出できない。「共通ヘルパーの引数リスト」と「別経路の `new` に渡す構造体のキー」を突き合わせ、生成自体を1つのヘルパーへ集約する。テストは既定値と異なる条件(ヘ音記号・リズム譜・非5線)で必ず1本置く

- **「表示状態を消費する要素」と「その状態に基づく記号を実際に描く要素」の集合がずれると、無関係な要素の記号まで黙って消える**
  - 説明: 臨時記号・オッターヴァ・ペダルのように「小節内・範囲内で効き続ける表示状態」を先に一括計算してから各要素へ配る構成では、状態計算(例: `measureAccidentals(measure.events, ...)`)が全イベントを走査する一方、描画側では特別な描かれ方をする要素(装飾音符・和音の2音目以降・不可視要素)が別経路で生成され、記号付与の共通ヘルパー(`toStaveNote` 等)を通らないことがある。この要素は「状態を消費するが記号は描かない」状態になり、自分の記号が出ないだけでなく、後続の通常要素が「同じ状態が既に提示済み」と判定されて記号を省略するため、範囲全体から記号が消える。データは正しいまま表示だけが誤るので、ラウンドトリップテストも再生テストも通る。VexFlow のように「StaveNote は臨時記号を自動描画せず Accidental modifier の明示付与が必要」なライブラリでは特に起きやすい。状態計算の入力集合と記号描画の対象集合を必ず一致させるか、記号付与を1つのヘルパーに閉じ込めて全生成経路から通す

- **長さの揃わない複数コレクションを同じ index 空間で描画すると、短い方が黙って「穴」になる**
  - 説明: 複数トラック(パート・レーン・系列)を縦に重ねて1本の時間軸で描く UI では、レイアウト(段割り・ページ割り)を「最長のコレクション」や特定の基準コレクションから求めつつ、実際の描画は各コレクション自身の `forEach` で回す構成になりやすい。この形だと要素数が揃っていないコレクションでは末尾側の index に描画が発生せず、同じ行の中で一部トラックだけ背景(五線・グリッド・枠)ごと消える。例外も警告も出ず、レイアウト計算のテスト(高さ・段数・添字外参照なし)は通るため、スクリーンショット確認まで気づかない。各トラックの走査を「レイアウト基準の index 範囲」に揃え、欠けている要素は空要素として背景だけ描くか、モデル側で要素数を揃える(要素追加操作を全トラックに効かせる)

- **start/stopペアを線で結ぶ描画で、参照テーブルに登録されない種類の要素を探索列に含めると線が黙って消える**
  - 説明: タイ・スラー・ブラケットのように start/stop の2要素を線で結ぶ描画では、描画済みオブジェクトを `Map<key, ref>` で引き直すのが定石だが、特殊な描かれ方をする要素(装飾音符・不可視休符など)は ref に登録されない一方で「イベント列」には残ることがある。`seq[idx + 1]` のような隣接探索がその要素に当たると ref 取得が undefined になり、例外も警告も出ないまま線だけが消える。探索列を作るときは「ref に登録される要素」と同じ条件でフィルタするか、特殊要素も ref に登録して両者の集合を一致させる

- **「レーン番号=表示行」を描画ライブラリの自動レイアウトに任せると、歯抜けレーンで行がずれる**
  - 説明: VexFlow の `Annotation`(BOTTOM) のように「同じ要素に複数の注釈を積む」APIは、行位置(textLine)を `addModifier` された順に state を積んで決めるだけで、こちらが持っているレーン番号(節番号・系列番号)は見ない。空のレーンを `if (!text) continue` で飛ばして積むと、レーン0が空でレーン1だけある要素は「レーン1の文字がレーン0の行」に描かれ、隣の要素と縦に揃わない。全レーンが埋まった入力では必ず正しく見えるため、歯抜けを許す機能(メリスマ・欠測系列)を後から足したときに初めて表面化する。しかも座標を実測して線を引く処理(ハイフン等)は「実際に描かれた位置」を使うぶん正しく動くので、線だけ正しく文字だけずれるという分かりにくい形になる。空レーンにも幅ゼロのプレースホルダを積んで行番号をレーン番号に一致させるか、行位置を明示設定する。テストは「レーン0が空でレーン1だけある要素」を必ず1本置く

### 状態管理(reducer)
- **範囲コピーの端で親を欠く従属要素は「落とす」でも「孤児のまま出す」でもなく、従属フラグを外した独立要素として持ち出す**
  - 説明: 装飾音符・子タスク・添付のような「親要素に紐づく従属要素」を範囲コピーの対象に含めると、範囲の端では親が範囲外になる。ここで従属要素を単に除外すると、カット=コピー+削除の実装では削除だけが実行されて内容が消え(かつコピー結果が空になり別モードへ落ちる二次被害を招く)、逆に従属フラグを付けたまま出すと貼り付け先で親を持たない孤児になり、描画も処理もされずデータだけが残る。どちらも例外は出ず、貼り付けて初めて気づく。第三の選択肢として「従属フラグ(grace/parentId等)と、その従属関係にのみ意味を持つ付随フィールドを外して独立要素に昇格させる」を検討し、コピー範囲内に親が含まれるかを判定するヘルパーを用意して、範囲の端だけを狙ったテストを1本置く

- **「削除が選択範囲より広い」場合、カット時のコピー範囲と選択ハイライトも同じ範囲に揃える**
  - 説明: 削除アクションが選択外の付随データ(装飾音符・アンカー・子要素など)まで巻き込むよう拡張したとき、cut = copy + delete の実装だと copy 側が旧来の選択範囲のままになり、カット→ペーストで付随データだけが失われる(Undo 以外に復元手段がない)。ハイライトも同様で、「選んでいないものが消えた」ように見える。削除範囲・コピー範囲・ハイライト範囲を同一の関数から導出して、食い違いを構造的になくす
- **コンテキスト切替アクションで関連stateをリセットし忘れる**
  - 説明: setActivePartのような「対象切替」アクションで、切替対象に依存するサブ状態(例: activeStaff)をリセット/クランプせず持ち越すと、新対象で不正な既定値や不正なフィールド付与が起き、データ破損につながる。切替時は対象に整合するよう関連stateを明示的に正規化する

### 一貫性
- **他フィールドから導出したフラグは、導出元を変える別コマンドでも再計算する**
  - 説明: 変換コマンド(例 toggleGrace)が「音価が8分以下なら斜線」のような導出フラグを生成時に一度だけ計算していると、あとから導出元(noteType・dots・連符比)を変える別コマンド(音価変更・付点循環)がフラグを更新せず、コード自身が立てた不変条件を破った状態が作れてしまう。導出式を関数に切り出し、導出元を変更する全パス(できれば共通の書き換えヘルパー1か所)から呼ぶか、その状態では導出元の変更を弾く

- **「AはBにできない」ガードを片方の変換コマンドにだけ入れると、逆方向の変換から同じ禁止状態が作れてしまう**
  - 説明: `toggleGrace`(休符→装飾音符を禁止)と `toggleRestNote`(装飾音符→休符が素通り)のように、同じ2属性を相互排他にしたい場合、ガードは「A→B」「B→A」の両方の変換コマンドに要る。片方だけだと禁止したはずの組み合わせがもう一方の経路から生成され、しかもその組み合わせは描画側で「壊れた入力への防御」として読み飛ばされる実装になっていることが多いため、要素が画面から消え・当たり判定も登録されず・再生もされない一方でデータとシリアライズ出力には残る、という発見しにくい形で現れる(例外もテスト失敗も出ない)。属性の相互排他ルールを増やしたら、その2属性を書き換える全コマンドを洗い出してガードを対にし、「禁止状態を作ろうとしても no-op」を両方向でテストする

- **描画側の探索列から除外した種類の要素は、編集コマンドの隣接探索からも同じ条件で除外する**
  - 説明: 「特殊要素(装飾音符・不可視要素・別レーン要素)を start/stop 探索列から除外する」修正を描画側に入れると、`nextEventCursorInVoice` のような編集コマンド側の隣接探索が取り残される。生成側は「次の要素」としてその特殊要素を選んで端点を書き込むが、描画側は列から外しているため、線が消える／別の要素まで伸びる／端点照合をしない実装では全く違う要素へ線が引かれる、といった形で現れる。例外は出ずデータも保存されるので、ラウンドトリップテストも再生テストも通る。範囲版(`setSlurRange` 等)にだけフィルタが入っていて単体版に無い、という非対称もできやすい。除外条件は描画と編集で共有し、特殊要素を挟んだ2要素に線を張るテストを単体・範囲の両パスに置く。その端点を再生側が解釈している場合(オッターヴァ等)は「描画されないのに再生だけ変わる」divergence になる点も確認する

- **同じ操作に「単体パス」と「一括(範囲選択)パス」がある場合、片方にだけ整合ガードを足すともう片方から同じ不整合が再発する**
  - 説明: reducer などで `case 'delete'` が「範囲選択あり→一括フィルタ」「なし→単体コマンド関数」と分岐しているとき、修正は単体コマンド側にだけ入りがち。関連レコードの連鎖削除・参照の掃除といった整合ガードは一括パスにも同じものが必要で、片方だけだと「特定の選択操作でだけ孤児データが残る」再現条件の狭いバグになる。ガードは共有ヘルパーへ切り出して両パスから呼び、一括パス側の回帰テストも併せて追加する

- **新しい action type を追加したとき、型で守られない「文字列リテラルの許可リスト(Set/配列)」への登録漏れが起きる**
  - 説明: reducer の action を discriminated union で定義しつつ、UI 側で `const EVENT_SCOPED_ACTIONS = new Set(['toggleTie', ...])` のように action.type の文字列を並べた許可リスト・自動補正リストを持つ構成では、union に新メンバーを足しても Set への追加漏れがコンパイルエラーにならない。結果として「同じボタン群の隣のボタンは未選択でも効くのに、新しいボタンだけ無反応」といった、機能ではなく一貫性の欠落として現れ、テストでも気づきにくい。新しい action を足したら `Set<EditorAction['type']>` のように型を付けて対象を絞るか、その action.type を列挙している全リストを grep して登録要否を判断する

- **同じモデル属性を扱う複数のコンシューマのうち片方だけ対応を足すと「音は変わるが画面に出ない」不一致になる**
  - 説明: 音声合成・アニメーション・レポート出力など、同じデータモデルを複数のコンシューマが独立に解釈する構成では、片方(例: 再生スケジューラ)にだけ新しい属性の扱いを追加すると、ユーザーには「操作した覚えのない変化」として現れ原因追跡が難しくなる。属性の解釈を追加するときは、そのモデルを読む全コンシューマを列挙して同時に更新するか、未対応側を明示的にコメント・テストで固定する

## データモデル・シリアライズ

- **「直前要素」に依存する外部フォーマット属性は、チャンク境界(小節・ページ・バッチ)をまたぐ直前要素も渡す**
  - 説明: MusicXML の `syllabic` のように「前の要素から続くか/次へ続くか」で値が決まる属性を出力するとき、シリアライズがチャンク単位(小節ごと等)の関数に分かれていると、`events[i - 1]` のようなローカル参照は各チャンクの先頭で必ず undefined になる。内部モデルは連結情報を「前の要素側」に持つことが多く自アプリのラウンドトリップは通るため、外部ツールで開いたときだけ連結が途切れる形で現れる。チャンクをまたぐ直前要素を引き回すか、連結対象をキーごとに保持する状態として持ち、テストは必ず境界をまたぐケースで置く

- **向き依存パラメータを常に始点へ格納すると外部フォーマットで意味が反転する**
  - 説明: ヘアピンのspreadのように「向きによって始点/終点どちらの値か」が変わる属性を、内部モデルの都合で一律に始点イベントへ持たせて MusicXML 等へ出力すると、crescendo/diminuendoの一方で仕様と逆の意味になり外部ツールで誤描画される。内部ラウンドトリップが通っても外部相互運用は別途検証し、向きに応じて出力先(start/stop)を切り替える

- **関連付けの「親」フラグを外す際に付随データを消し忘れると孤児フィールドが残り再利用時に復活する**
  - 説明: wedgeStartを外すのにwedgeSpreadを残すように、開始マーカーをundefinedにしても付随パラメータをクリアしないと、同じ要素に機能を張り直したとき古い値が予期せず甦る。マーカー解除時は依存フィールドも一括で初期化する

- **範囲張り替え操作で範囲外に残るペア端点(相方)を掃除しないと孤児端点が残る**
  - 説明: スラー・松葉のような start/stop ペアを持つ要素に対し「選択範囲へ張り替える」操作を実装する際、範囲内の端点だけを再割り当てし、範囲を跨いで範囲外に存在する相方の端点(既存スラーの stop が範囲より後ろ、start が範囲より前 等)をクリアしないと、start と stop の対応が崩れ孤児端点が残る。MusicXML 等の外部出力で不整合・誤描画を招く。範囲操作では範囲の前後を辿って範囲を跨ぐ既存ペアの外側端点も掃除する

- **「次へ続く」フラグをそのまま外部フォーマットの開始マーカーへ写すと、列の末尾で相方のない開始マーカーが残る**
  - 説明: MusicXML の `syllabic`(begin/middle) のように「次の要素へ続く」を表す値を、内部モデルの `continuesToNext` フラグだけから決めて出力すると、後続要素が実在しない場合(語末ハイフンの入力、割付が途中で尽きた、範囲コピーの端)に end のない begin が出力される。描画側は「次が無ければ何も描かない」と自然に握りつぶし、パースし直しても同じフラグに戻るのでラウンドトリップテストも通り、外部ツールで開いたときだけ壊れて見える。開始マーカーを出す条件には「同じキー(節・声部・系列)に後続要素が実在するか」を必ず含め、無ければ single/end へ降格させる。テストは列の最後の要素に continuesToNext を立てたケースで置く

## セキュリティ

- **共有トークンで外部リソースを読む API をユーザー認証のみでゲートすると全ユーザーに共有リソース全体が露出する**
  - 説明: 運営の Internal Integration トークンや共有 API キーなど「ユーザー個別ではない」資格情報でデータを取得する API ルートを、単なる `verifyIdToken`（ログイン確認）だけで保護すると、認証済みの全ユーザーが共有リソース（他人/運営のデータ）にアクセス・取り込みできてしまう。既存の「自分のリソースを守るための verifyIdToken」パターンと混同しないよう、共有トークン参照 API は dev/管理者ロールや環境フラグで別途ゲートする
