# Shell レビューチェックリスト

## よくあるミス

### 検証ロジック
- **パイプで繋いだ複数 grep は「同じ行」しか保証せず「同じレコード」は保証しない**
  - 説明: `grep A file | grep -q B` は JSONL のように1行に複数レコードが載る形式では、A と B が別レコード由来でも真になる。認証・免除・ゲート解除の判定に使うと偽装・誤検知の穴になる
  - 例:
    ```sh
    # NG: 同一行というだけで、同じ tool_result 由来とは限らない
    grep -F "$ERR" "$transcript" | grep -qF '"is_error":true'

    # OK: 構造をパースし、対応関係(id)で突き合わせる
    jq -e --arg e "$ERR" 'select(.is_error and (.content | startswith($e))) | .tool_use_id' "$transcript"
    ```
  - 対策: 構造化データは jq 等でパースし、対応関係(tool_use_id など)で突き合わせる

### セキュリティ
- **外部入力(session_id 等)を検証せずファイルパスに連結しない**
  - 説明: フックの JSON 入力から取った値をそのままパスに埋め、`: >` や `rm` の対象にすると、区切り文字や `../` の混入でディレクトリ外を破壊しうる
  - 例:
    ```sh
    # NG
    : > "$dir/$sid.marker"

    # OK: 許可文字クラスで弾いてから使う
    case "$sid" in *[!a-zA-Z0-9_-]*|'') sid="" ;; esac
    ```
  - 対策: 許可文字クラスでのバリデーションを挟む

### パターンマッチ
- **`case "$cmd" in *" -x"*)` によるフラグ判定はコマンド文字列全体に一致する**
  - 説明: 先頭トークンで対象を絞った後にフラグを部分一致で見ると、パイプや `&&` で連結された後続コマンドの引数にも一致する
  - 例:
    ```sh
    # `ls src && sort -S 1M f.txt` が ls の -S 免除に引っかかる
    case "$cmd" in *" -S"*) exit 0 ;; esac
    ```
  - 対策: 対象コマンドの引数列だけを切り出してから照合する。切り出しは引用符の外の区切り文字だけを見る(`echo 'a;b' > f` が引用符内の `;` で切れて判定を迂回する)

- **`for w in $var` の非クォートは単語分割だけでなくパス名展開も行う**
  - 説明: 引数列をトークンに割る目的で非クォート展開を使うと、`*` `?` `[` を含む語がフック実行時の cwd に対してグロブ展開され、判定対象が元のコマンド行と別物になる
  - 対策: `set -f` / `set +f` でグロブを抑止してからループする

### 環境変数
- **数値として使う環境変数は `[ ... -lt ... ]` に渡す前に数値検証する**
  - 説明: `set -e` なしのスクリプトで `[ "$a" -lt "$b" ]` に非数値が入ると、stderr にエラーを出したうえで条件が偽扱いになりフォールスルーする。閾値の上書きや無効化用の env を誤記したときに、意図と逆の分岐(常にブロック等)へ倒れる
  - 例:
    ```sh
    threshold="${FC_TOOLCALLS:-400}"
    case "$threshold" in ''|*[!0-9]*) threshold=400 ;; esac
    ```
  - 対策: 使用前に許可文字クラスで正規化し、既定値へ落とす

### フック連携
- **直列ディスパッチャに新しいゲートを差し込むときの後続ゲート取りこぼし**
  - 説明: Stop フックを複数直列に呼ぶディスパッチャでは、前段が block すると継続後の Stop 入力が `stop_hook_active=true` になり、後段のゲートも自前のループ防止で即 exit してそのターン一度も走らない。各ゲート単体のテストでは検出できない
  - 対策: ゲートは「どちらかが block したら残りを飛ばす」ではなく必ず全部走らせて理由を連結する。ディスパッチャレベルの結合テスト(前段 block でも後段が走ること)を1本置く

### transcript 判定
- **記録形式を推測して正規表現を書く**
  - 説明: スラッシュコマンドは `<command-message>name</command-message>\n<command-name>/name</command-name>` の形で記録され、`/compact` などの組み込みだけが `<command-name>` 直開始(先頭に空白が入ることもある)。形を推測して `^<command-name>` にアンカーすると恒久的に空振りする
  - 対策: `~/.claude/projects/**/*.jsonl` を実際に読んで形式を確認する。**テストフィクスチャも実データから写す**(自作フィクスチャに合わせた正規表現は空振りのまま pass する)

- **判定パターン自体をソースやドキュメントに書くと写り込みで偽陽性になる**
  - 説明: 「Read した本文は JSON エスケープされるから一致しない」という前提はクォートを含むパターンにしか成り立たない。JSON は `/` `<` `>` をエスケープしないため、タグ形式のパターンはソースコメント・テストデータ・`git diff` 出力が transcript に載った時点で一致する
  - 対策: 文字列一致ではなく jq でレコード種別(`.type`)と位置(`startswith` / `test` のアンカー)まで構造的に検証する

- **スキル/コマンド実行の痕跡を単一の記録形式だけで検出しない**
  - 説明: スキル実行は Skill ツール呼び出し(`"skill":"..."`)とスラッシュコマンドの2形式で記録され、スラッシュ経由では Skill ツール呼び出しが発生しない
  - 対策: 両形式を OR で照合する

### 状態キャッシュ
- **セッション単位のキャッシュキーが実行コンテキストを跨ぐ**
  - 説明: フックの `session_id` は親セッションとサブエージェントで共有される一方、利用可能ツールはコンテキストごとに異なる。`session_id` だけをキーに免除マーカーを永続化すると、片方で成立した緩和が他方へ漏れ、ガードがセッション終了まで無効化される
  - 対策: キーには `transcript_path` などコンテキストを一意に識別する値を含める

- **block の reason に書いた回避手段が状態をリセットしない**
  - 説明: Stop フックの `stop_hook_active` は直後の再停止1回しか抑止しない。reason に「不要なら理由を書けばよい」と案内しても、その行為はカウンタを変えないため次のターン末で同じ条件が再成立し、毎ターン差し戻しが続く
  - 対策: 回避手段が満たされたことを検出できる形(マーカーファイル等)にするか、reason から回避手段を削って出口を一本化する

### 閾値設計
- **発火閾値を実データを数えずに決める**
  - 説明: フックやゲートの発火閾値を推測で置くと、実運用の分布と桁で外れる。「たまに発火する」つもりが全セッションで常時発火になる
  - 対策: 手元に実データ(transcript 等)があるなら閾値候補ごとの発火回数を数えてから決め、根拠をコメントに残す

### CI 出力サイズ
- **外部サービスのサイズ上限を一部分の長さだけで判定する**
  - 説明: Issue 本文のように上限のある出力を複数の断片から組み立てるとき、断片の一つだけを閾値と比べて縮約を決めると、合計が上限を超えて API 呼び出しが失敗する。CI ではその step の失敗で後続の通知 step も止まり、何も通知されない
  - 対策: 組み立てた出力全体で判定するか、断片ごとに上限を割り当ててそれぞれの生成側で縮める

### CI 環境変数
- **件数に比例して伸びる値を `env:` や `GITHUB_ENV` で渡さない**
  - 説明: GitHub Actions の `env:` / `GITHUB_ENV` の値はプロセスの環境変数になる。Linux は1変数約 128 KiB(MAX_ARG_STRLEN)が上限で、超えると step がシェル起動前に `Argument list too long` で落ちる。受け取り側に「長すぎたら縮める」処理を置いても step 自体が起動しないので効かない
  - 対策: 生成側で長さを測って縮めるか、ファイルや artifact で渡す

### CI での LLM CLI 実行
- **`claude -p` の書き込み許可を `Write(<絶対パス>/**)` で書いても一致せず、黙って拒否される**
  - 説明: `-p` は許可確認を出さないので、範囲外の Write は拒否されたまま終了コード 0 で終わり、出力ファイルが無い。`--allowedTools "Write(${dir}/**)"` は実測で拒否された。逆に引数なしの `Write` を許可すると全域に書ける。ローカルではユーザー設定の許可で通ってしまい、CI でだけ落ちる
  - 対策: 出力先を作業ディレクトリにして `--permission-mode acceptEdits` で書き込み範囲を限る(`--add-dir` でも可)。成否は CLI の終了コードではなく、期待する出力ファイルがあるかで判定する。ローカル検証は `--setting-sources project` でユーザー設定を外して行う

- **書き込みを作業ディレクトリに限っても、読み取りは作業ディレクトリの外に及ぶ**
  - 説明: `claude -p` を acceptEdits と作業ディレクトリの組み合わせで動かすと、書き込みは閉じ込められるが、Read/Glob/Grep は既定でディレクトリ外も読める。外部データ（ログ・Issue 本文など）由来のプロンプトインジェクションで、ランナーの一時ディレクトリに置いた MCP 設定の API キーや、checkout が `.git/config` に残すトークンを読み、出力ファイル経由で通知先へ流せる
  - 対策: `--tools Write` のように組み込みツールを必要最小限に絞る（実測で範囲外の Read 不可・Write 可）。checkout は `persist-credentials: false` にする

### CI 失敗通知
- **生成ステップが途中で失敗しても、残った出力ファイルを後続の通知ステップが正常として送る**
  - 説明: 生成ステップを `continue-on-error` にし、通知ステップを `if: always()` で「出力ファイルがあれば通常通知、無ければ失敗通知」と分けると、生成側が出力の一部を書いた後に失敗したとき、失敗が正常な通知として届く
  - 対策: 通知ステップに生成ステップの `outcome` を渡し、success 以外ならファイルの有無にかかわらず失敗通知にする。生成側の冒頭で前回の出力を消しておく

### 分類ロジック
- **対応方法の振り分けで「修正版の有無」を一部の分岐でしか見ない**
  - 説明: 検出を種類ごとに対応方法(再ビルド・依存更新 PR・個別確認)へ振り分けるとき、修正版の有無を一つの分岐でしか確かめないと、修正版のない検出まで自動対応できる扱いになり、案内と実態が食い違う
  - 対策: 自動対応を案内するすべての分岐で修正版の有無を条件に入れる

### jq 集約
- **1レコード内の配列を属性ごとに別々に `unique` して列に並べない**
  - 説明: `[.items[] | .a] | unique` と `[.items[] | .b] | unique` を列として並べると、ソートと重複除去が列ごとに独立して行われ、同じ要素の a と b の対応が崩れる。重複除去で要素数もずれる
  - 対策: 要素ごとに行を出すか、`"\(.a) \(.b)"` のように組を作ってから `unique` する

### 定時実行
- **launchd や cron から `zsh -lc` で起動すると、対話シェル用の rc ファイルで設定した PATH と環境変数が入らない**
  - 説明: ログインシェルでも対話シェルでなければ `.zshrc`(bash なら `.bashrc`)は読まれない。PATH の追加や通知用の環境変数を rc 側に置いていると、定時実行では外部コマンドが見つからず、通知も空のまま失敗する。PATH にスタブを通すテストでは検出できない
  - 対策: PATH をスクリプトか plist に明示する。起動前に `command -v` で必要なコマンドを確かめ、無ければ失敗として記録する。`env -i HOME=$HOME zsh -lc 'command -v …'` で実際の起動環境を再現して確かめる
- **スクリプト内で PATH を補うとき、先頭に足すとテストのスタブより本物のコマンドが優先される**
  - 説明: `PATH="/opt/homebrew/bin:$PATH"` のように前へ足すと、呼び出し側が PATH の先頭に置いた偽コマンドより標準の場所にある本物が先に見つかる。テストが本物の CLI(LLM の CLI、デプロイコマンドなど)を実際に起動し、時間と費用がかかるうえ副作用が出うる
  - 対策: 不足分は後ろに足す(`PATH="$PATH:/opt/homebrew/bin"`)。テストには「スタブが呼ばれたこと」を確かめる検査を1本置く
- **macOS の `hostname -s` を対象マシンの判定に使うと、ネットワークによって値が変わり、ジョブが黙ってスキップされる**
  - 説明: macOS で `HostName` が未設定だと、`hostname` の値は DHCP や逆引き DNS から決まり、接続するネットワークで変わりうる。この値と一致したときだけ実行する作りだと、名前が変わった日から「対象外」として exit 0 で抜け続け、結果ファイルも通知も更新されない
  - 対策: `sudo scutil --set HostName <名前>` で固定するか、変わらない識別子を使う。スキップしたことも結果に残して通知する
- **準備の途中の `ln -s` や `cp` の失敗を確かめず、そのまま本処理へ進む**
  - 説明: リンク先の親ディレクトリが無い(git 管理外なので worktree に作られない)と `ln -s` は失敗するが、準備は成功として扱われ、認証情報などが無いまま本処理が走る
  - 対策: 準備の中で失敗しうるコマンドには、どれも `|| return 1` を付ける
- **長期の認証トークンを設定ファイルから読んでスクリプト全体で export すると、準備コマンドにも渡る**
  - 説明: 無人実行のために認証トークンを読み、本処理より前に export すると、準備段階で走る依存インストール(パッケージのライフサイクルスクリプト)や git フックにも継承され、外部コードが認証情報を読める
  - 対策: 値はシェル変数に入れておき、使うコマンドを起動する直前(そのコマンド専用のサブシェル内)でだけ export する。準備コマンドから見えないことをテストで確かめる

### プロセス管理
- **SIGTERM を1回送るだけの時間切れ処理は、対象が終わらなければ wait が永久に戻らず、ロックも残り続ける**
  - 説明: 監視用サブシェルが TERM を送って `wait $pid` するだけだと、対象が TERM を無視したり終了処理で止まったりしたときに親が戻らない。ロックの持ち主が生きているので後続の実行は「実行中」として黙ってスキップされ続ける。対象が起動した子プロセスも取り残される
  - 対策: 対象を別のプロセスグループで起動し(`set -m`)、猶予を置いてグループごと KILL する。古すぎるロックを見つけたら通知する。sleep を止めた後に監視側が次の行へ進む競合を防ぐため、監視側は `trap 'kill $sleeper; exit 0' TERM; sleep N & sleeper=$!; wait $sleeper` の形にする
- **`trap '… "$local_var"' EXIT` を関数の中で張ると、発火時には local 変数が見えない**
  - 説明: EXIT の trap はスクリプトの終了時に走る。関数内の `local` 変数はその時点でスコープの外なので空に展開され、`rm -rf ""` のように何もしないコマンドになる。ロックや一時ファイルが消えずに残る
  - 対策: trap から参照する値はグローバル変数に入れてから trap を張る。テストで「終了後に消えていること」を確かめる
- **外部から TERM を受けたときの trap が、子へ TERM を送るだけでロックを外し、結果も残さない**
  - 説明: 時間切れの経路では猶予のあと KILL して結果を記録するのに、親が外から止められた経路(launchd の再登録やログアウト)ではそれをしない作りが多い。止まりきっていない子が残ったままロックが消え、次の回と同時に動く。結果ファイルには前回の成功が残る
  - 対策: 外からの停止も時間切れと同じ手順(猶予 → KILL → wait → 結果の記録)で終える

### テスト安全性
- **環境に依存して検査を飛ばす判定が、危険な操作の後に置かれている**
  - 説明: 「このマシンには本物のコマンドがあるので検査しない」のような判定を、対象のコマンドを実行した後に書くと、飛ばすべき環境でも本物が先に起動してしまう
  - 対策: 判定は実行より前に置き、実行そのものを分岐の中に入れる。できれば環境まかせにせず、本体が補う PATH を環境変数で空にできるようにして、どのマシンでも同じ条件を作る
- **親プロセスの `GIT_CONFIG_COUNT` などの環境変数が、テスト内の git に効く**
  - 説明: 呼び出し元が `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_n` / `GIT_CONFIG_VALUE_n` や `GIT_DIR` で git の設定を差し込んでいると、テストが作る一時リポジトリの push や commit にも効いてテストが落ちる。単体で実行すると通るので気づけない
  - 対策: git を使うテストは冒頭で `GIT_CONFIG_*`、`GIT_DIR`、`GIT_WORK_TREE`、`GIT_INDEX_FILE` を unset する。テストを起動する側も、これらを落とした環境で起動する
- **`$var` の直後に全角文字を続けて書くと、ロケールによって変数名の一部として読まれる**
  - 説明: `"$detail。続き"` のように波括弧なしで全角文字を続けると、ロケールが未設定の環境(定時実行など)で展開結果が壊れる。対話シェルでは再現しないことがある
  - 対策: 文字列の中で変数の直後に ASCII 以外が来るときは `${var}` と書く
- **除外するはずの対象が別の条件でもともと除外されていて、テストが何も確かめていない**
  - 説明: 「接頭辞の違うものは数えない」を確かめるのに、merge 済みのような別のフィルタでも落ちる対象を使うと、確かめたいフィルタを外してもテストが通る
  - 対策: 確かめる条件以外はすべて満たす対象を用意する。フィルタを外したらテストが落ちることを一度確かめる
- **検査スクリプトを一時ファイルに取り出して実行すると、取り出しの失敗で空のスクリプトが「合格」になる**
  - 説明: `f=$(mktemp) && git show <rev>:<path> > "$f"` の次の行で `python3 "$f"` や `bash "$f"` を実行すると、取り出しに失敗したときは空ファイルが実行されて終了コード 0 になる。終了コードで合否を決める手順では、検査が飛ばされたことに気づけない
  - 対策: 取り出しと実行を `&&` でつなぎ、`[ -s "$f" ]` でも確かめる
- **時間で変わる状態を「変わらない」と決めて、肯定の判定を永続キャッシュにする**
  - 説明: 「この資源は無い」という判定をマーカーファイルに残して次から読み直さない作りは、資源が後から増える環境で、古い判定のまま許可し続ける
  - 対策: 根拠にした記録が変わりうるなら残さず毎回判定する。残すなら、根拠にした記録の版(ハッシュ)をキーに含める
- **`stat -f %Lp f || stat -c %a f` の順に試すと、GNU の環境で出力が混ざる**
  - 説明: GNU の stat は `-f` を「ファイルシステムの情報」と解釈し、何か出力してから失敗する。その出力が `||` の後の出力と連結され、権限の比較が必ず食い違う
  - 対策: GNU の形(`-c %a`)を先に試すか、出力が数字だけかを確かめてから採用する
- **永続設定を点検するスクリプトが、呼び出し元のシェルから受け継いだ環境変数で OK と判定する**
  - 説明: 設定ファイルから環境変数へ読み込んでから「変数があるか」で点検すると、対話シェルで export 済みの値でも合格になる。デーモンやスケジューラはその環境を受け継がないため、本番では設定が無いまま動く
  - 対策: 判定の前にその変数を unset してから読み込むか、ファイルから読めた値だけで判定する

### git の設定
- **環境変数で入れた複数値の git 設定は、既存の値に追加されるだけで置き換わらない**
  - 説明: `GIT_CONFIG_COUNT` などで remote の `pushurl` を差し込んでも、リポジトリ側に `pushurl` があれば値が増えるだけで、git は全部に push する。`url.<base>.pushInsteadOf` は明示された `pushurl` には効かず、列挙した接頭辞に当たらない相対パスも素通りする
  - 対策: push を止めたいときは宛先の書き換えだけに頼らず、push の直前に必ず呼ばれる pre-push フック(`core.hooksPath` で差し替える)でも止める。既存の値があれば実行せずに知らせる

### CLI 引数
- **副作用を抑えるフラグを完全一致でしか見ず、知らない引数を無視する**
  - 説明: `[ "$2" = "--dry-run" ] && dry=1` だけだと、打ち間違いや余分な引数が黙って無視され、本番の処理(外部への投稿・マージ・課金のかかる API 呼び出し)が走る
  - 対策: 安全側のフラグを持つコマンドは、知らない引数をエラーにする
