# Shell レビューチェックリスト

## よくあるミス

### 検証ロジック
- **パイプで繋いだ複数 grep は「同じ行」しか保証せず「同じレコード」は保証しない**
  - 説明: `grep A file | grep -q B` は JSONL のように1行に複数レコードが載る形式では、A と B が別レコード由来でも真になる。認証・免除・ゲート解除の判定に使うと偽装・誤検知の穴になる
  - 例:
    ```sh
    # NG: 同一行というだけで、同じ tool_result 由来とは限らない
    grep -F "$ERR" "$transcript" | grep -qF '"is_error":true'

    # OK: 構造をパースし、対応関係(id)で突き合わせる
    jq -e --arg e "$ERR" 'select(.is_error and (.content | startswith($e))) | .tool_use_id' "$transcript"
    ```
  - 対策: 構造化データは jq 等でパースし、対応関係(tool_use_id など)で突き合わせる

### セキュリティ
- **外部入力(session_id 等)を検証せずファイルパスに連結しない**
  - 説明: フックの JSON 入力から取った値をそのままパスに埋め、`: >` や `rm` の対象にすると、区切り文字や `../` の混入でディレクトリ外を破壊しうる
  - 例:
    ```sh
    # NG
    : > "$dir/$sid.marker"

    # OK: 許可文字クラスで弾いてから使う
    case "$sid" in *[!a-zA-Z0-9_-]*|'') sid="" ;; esac
    ```
  - 対策: 許可文字クラスでのバリデーションを挟む

### パターンマッチ
- **`case "$cmd" in *" -x"*)` によるフラグ判定はコマンド文字列全体に一致する**
  - 説明: 先頭トークンで対象を絞った後にフラグを部分一致で見ると、パイプや `&&` で連結された後続コマンドの引数にも一致する
  - 例:
    ```sh
    # `ls src && sort -S 1M f.txt` が ls の -S 免除に引っかかる
    case "$cmd" in *" -S"*) exit 0 ;; esac
    ```
  - 対策: 対象コマンドの引数列だけを切り出してから照合する。切り出しは引用符の外の区切り文字だけを見る(`echo 'a;b' > f` が引用符内の `;` で切れて判定を迂回する)

- **`for w in $var` の非クォートは単語分割だけでなくパス名展開も行う**
  - 説明: 引数列をトークンに割る目的で非クォート展開を使うと、`*` `?` `[` を含む語がフック実行時の cwd に対してグロブ展開され、判定対象が元のコマンド行と別物になる
  - 対策: `set -f` / `set +f` でグロブを抑止してからループする

### 環境変数
- **数値として使う環境変数は `[ ... -lt ... ]` に渡す前に数値検証する**
  - 説明: `set -e` なしのスクリプトで `[ "$a" -lt "$b" ]` に非数値が入ると、stderr にエラーを出したうえで条件が偽扱いになりフォールスルーする。閾値の上書きや無効化用の env を誤記したときに、意図と逆の分岐(常にブロック等)へ倒れる
  - 例:
    ```sh
    threshold="${FC_TOOLCALLS:-400}"
    case "$threshold" in ''|*[!0-9]*) threshold=400 ;; esac
    ```
  - 対策: 使用前に許可文字クラスで正規化し、既定値へ落とす

### フック連携
- **直列ディスパッチャに新しいゲートを差し込むときの後続ゲート取りこぼし**
  - 説明: Stop フックを複数直列に呼ぶディスパッチャでは、前段が block すると継続後の Stop 入力が `stop_hook_active=true` になり、後段のゲートも自前のループ防止で即 exit してそのターン一度も走らない。各ゲート単体のテストでは検出できない
  - 対策: ゲートは「どちらかが block したら残りを飛ばす」ではなく必ず全部走らせて理由を連結する。ディスパッチャレベルの結合テスト(前段 block でも後段が走ること)を1本置く

### transcript 判定
- **記録形式を推測して正規表現を書く**
  - 説明: スラッシュコマンドは `<command-message>name</command-message>\n<command-name>/name</command-name>` の形で記録され、`/compact` などの組み込みだけが `<command-name>` 直開始(先頭に空白が入ることもある)。形を推測して `^<command-name>` にアンカーすると恒久的に空振りする
  - 対策: `~/.claude/projects/**/*.jsonl` を実際に読んで形式を確認する。**テストフィクスチャも実データから写す**(自作フィクスチャに合わせた正規表現は空振りのまま pass する)

- **判定パターン自体をソースやドキュメントに書くと写り込みで偽陽性になる**
  - 説明: 「Read した本文は JSON エスケープされるから一致しない」という前提はクォートを含むパターンにしか成り立たない。JSON は `/` `<` `>` をエスケープしないため、タグ形式のパターンはソースコメント・テストデータ・`git diff` 出力が transcript に載った時点で一致する
  - 対策: 文字列一致ではなく jq でレコード種別(`.type`)と位置(`startswith` / `test` のアンカー)まで構造的に検証する

- **スキル/コマンド実行の痕跡を単一の記録形式だけで検出しない**
  - 説明: スキル実行は Skill ツール呼び出し(`"skill":"..."`)とスラッシュコマンドの2形式で記録され、スラッシュ経由では Skill ツール呼び出しが発生しない
  - 対策: 両形式を OR で照合する

### 状態キャッシュ
- **セッション単位のキャッシュキーが実行コンテキストを跨ぐ**
  - 説明: フックの `session_id` は親セッションとサブエージェントで共有される一方、利用可能ツールはコンテキストごとに異なる。`session_id` だけをキーに免除マーカーを永続化すると、片方で成立した緩和が他方へ漏れ、ガードがセッション終了まで無効化される
  - 対策: キーには `transcript_path` などコンテキストを一意に識別する値を含める

- **block の reason に書いた回避手段が状態をリセットしない**
  - 説明: Stop フックの `stop_hook_active` は直後の再停止1回しか抑止しない。reason に「不要なら理由を書けばよい」と案内しても、その行為はカウンタを変えないため次のターン末で同じ条件が再成立し、毎ターン差し戻しが続く
  - 対策: 回避手段が満たされたことを検出できる形(マーカーファイル等)にするか、reason から回避手段を削って出口を一本化する

### 閾値設計
- **発火閾値を実データを数えずに決める**
  - 説明: フックやゲートの発火閾値を推測で置くと、実運用の分布と桁で外れる。「たまに発火する」つもりが全セッションで常時発火になる
  - 対策: 手元に実データ(transcript 等)があるなら閾値候補ごとの発火回数を数えてから決め、根拠をコメントに残す

### CI 出力サイズ
- **外部サービスのサイズ上限を一部分の長さだけで判定する**
  - 説明: Issue 本文のように上限のある出力を複数の断片から組み立てるとき、断片の一つだけを閾値と比べて縮約を決めると、合計が上限を超えて API 呼び出しが失敗する。CI ではその step の失敗で後続の通知 step も止まり、何も通知されない
  - 対策: 組み立てた出力全体で判定するか、断片ごとに上限を割り当ててそれぞれの生成側で縮める

### CI 環境変数
- **件数に比例して伸びる値を `env:` や `GITHUB_ENV` で渡さない**
  - 説明: GitHub Actions の `env:` / `GITHUB_ENV` の値はプロセスの環境変数になる。Linux は1変数約 128 KiB(MAX_ARG_STRLEN)が上限で、超えると step がシェル起動前に `Argument list too long` で落ちる。受け取り側に「長すぎたら縮める」処理を置いても step 自体が起動しないので効かない
  - 対策: 生成側で長さを測って縮めるか、ファイルや artifact で渡す

### CI での LLM CLI 実行
- **`claude -p` の書き込み許可を `Write(<絶対パス>/**)` で書いても一致せず、黙って拒否される**
  - 説明: `-p` は許可確認を出さないので、範囲外の Write は拒否されたまま終了コード 0 で終わり、出力ファイルが無い。`--allowedTools "Write(${dir}/**)"` は実測で拒否された。逆に引数なしの `Write` を許可すると全域に書ける。ローカルではユーザー設定の許可で通ってしまい、CI でだけ落ちる
  - 対策: 出力先を作業ディレクトリにして `--permission-mode acceptEdits` で書き込み範囲を限る(`--add-dir` でも可)。成否は CLI の終了コードではなく、期待する出力ファイルがあるかで判定する。ローカル検証は `--setting-sources project` でユーザー設定を外して行う

- **書き込みを作業ディレクトリに限っても、読み取りは作業ディレクトリの外に及ぶ**
  - 説明: `claude -p` を acceptEdits と作業ディレクトリの組み合わせで動かすと、書き込みは閉じ込められるが、Read/Glob/Grep は既定でディレクトリ外も読める。外部データ（ログ・Issue 本文など）由来のプロンプトインジェクションで、ランナーの一時ディレクトリに置いた MCP 設定の API キーや、checkout が `.git/config` に残すトークンを読み、出力ファイル経由で通知先へ流せる
  - 対策: `--tools Write` のように組み込みツールを必要最小限に絞る（実測で範囲外の Read 不可・Write 可）。checkout は `persist-credentials: false` にする

### CI 失敗通知
- **生成ステップが途中で失敗しても、残った出力ファイルを後続の通知ステップが正常として送る**
  - 説明: 生成ステップを `continue-on-error` にし、通知ステップを `if: always()` で「出力ファイルがあれば通常通知、無ければ失敗通知」と分けると、生成側が出力の一部を書いた後に失敗したとき、失敗が正常な通知として届く
  - 対策: 通知ステップに生成ステップの `outcome` を渡し、success 以外ならファイルの有無にかかわらず失敗通知にする。生成側の冒頭で前回の出力を消しておく

### 分類ロジック
- **対応方法の振り分けで「修正版の有無」を一部の分岐でしか見ない**
  - 説明: 検出を種類ごとに対応方法(再ビルド・依存更新 PR・個別確認)へ振り分けるとき、修正版の有無を一つの分岐でしか確かめないと、修正版のない検出まで自動対応できる扱いになり、案内と実態が食い違う
  - 対策: 自動対応を案内するすべての分岐で修正版の有無を条件に入れる

### jq 集約
- **1レコード内の配列を属性ごとに別々に `unique` して列に並べない**
  - 説明: `[.items[] | .a] | unique` と `[.items[] | .b] | unique` を列として並べると、ソートと重複除去が列ごとに独立して行われ、同じ要素の a と b の対応が崩れる。重複除去で要素数もずれる
  - 対策: 要素ごとに行を出すか、`"\(.a) \(.b)"` のように組を作ってから `unique` する
