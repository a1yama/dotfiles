# 文章を引き締める

## このスキルが解こうとしている問題

冗長な文章の正体は「長さ」ではなく「情報を持たない語」である。だから字数目標から入ってはいけない。字数を目標にすると条件節や例外まで削られ、意味が変わる。順序は逆で、先に情報を棚卸しし、情報のない語を消す。短さは結果として付いてくる。

構造にも問題がある。AIが書いた社内ドキュメントは「背景 → 本論 → まとめ」の形をとりながら、背景が既知情報の言い換えで、まとめが本論の言い換えであることが多い。同じことを3回読ませられるので読む気が失せる。文単位の推敲より、この重複を落とすほうが効果が大きい。

そしてもう一つ、**冗長さを削るだけではAIっぽさは消えない**。むしろ悪化しうる。文を短く整え、段落の文数を揃え、全部を同じ調子の敬体で書き切ると、読みやすいのに「機械が書いた」と分かる文章になる。AIっぽさの正体の一つは均質性だからだ。だから作業は2系統ある。**情報のない語を削る（冗長さ）**と、**均質さを崩す（AIっぽさ）**。前者だけやって後者を忘れると、短くて無味無臭な文章になる。

順序は、構造 → 文 → 語 → 表層。最後に lint で機械判定して取りこぼしを拾う。

## 手順

### 0. 触ってはいけない領域を確定する

添削で最も起きやすい事故は、直してはいけないものを直すことだ。以下は原文のまま通す。

- コードブロック、コマンド、ログ、スタックトレース
- 表の中の数値・データ
- frontmatter、設定値、環境変数名、APIのパラメータ名
- URL、リンクテキスト
- 引用（他人の発言、議事録の発言記録、規約の条文）
- 仕様として意味を持つ数値・バージョン・エラーコード

見出しや箇条書きは触ってよい。迷ったら触らず「確認したいこと」に回す。

### 1. 読み手と目的を1行で確定する

「誰が、これを読んで、何を決める／何をするのか」。これが決まらないと何が情報で何がノイズかを判定できない。原文から読み取れるなら書き留めるだけでよい。読み取れないときは推測を明示して進め、最後の「確認したいこと」に載せる。

あわせて確認しておくと効く問い：**この文書は誰の問題を解くのか。成功を何で判断するのか。例外をどこまで扱うのか。** 3つめが特に効く。例外の扱いが決まっていない文書は、読み手が「じゃあこの場合は？」で止まる。

例：「開発チームのレビュアーが、この設計で進めてよいか判断するための文書」

### 2. 情報を棚卸しする

段落ごとに、含まれている**事実・数字・判断・依頼・条件**を書き出す。何も書き出せない段落は、丸ごと削除候補である。ここで「この段落は雰囲気を作っている」と擁護したくなるが、社内ドキュメントに雰囲気は不要。

このとき、**固有名詞と数字が1つも出てこない段落**に印を付ける。抽象語だけで組み立てられた段落は、削るか、具体を足すかのどちらかしかない。判断は書き手に返す。

### 3. 構造を組み直す

- 結論・決定事項・依頼を冒頭に置く。読み手が最初の3行で「自分は何をすべきか」を知れる状態にする。
- 既知情報の再説明である「はじめに」「背景」は削るか1行にする。読み手が本当に知らないことだけ残す。
- 本論の言い換えである「まとめ」は削る。残すのは決定事項・ToDo・未決事項のような、本論には無かった情報だけ。
- 見出しの下は1トピック。2つ入っていたら見出しを割る。
- 比較・条件分岐・項目対応は表にする。散文で並べると読み手が頭の中で表を再構築させられる。
- **両論併記を畳む。** 「〜という意見もあれば、〜という意見もある」で終わっている箇所は、書き手の判断が抜けている。原文から読み取れるなら立場を出す。読み取れないなら「どちらで進めるか未決」と書く。並べただけの状態が一番読み手を止める。

### 4. 文を圧縮する。ただし均質化させない

- 一文は一主張。「〜であり、〜のため、〜となる」は分割する。
- ヘッジの重ね掛けをやめる。断定できるなら断定し、できないなら「未確認」と書いて根拠を示す。「〜と考えられる可能性があります」は何も言っていない。
- 名詞化した述語は動詞に戻す。「対応を実施する」→「対応する」。
- 冒頭の接続詞（また、さらに、そのため、一方で）は半分以上が削れる。論理関係が本当に必要なところだけ残す。
- 二重否定は肯定形にする。

ここで**やってはいけないこと**が2つある。どちらも「読みやすくしよう」とすると自然にやってしまうので、意識して避ける。

**文長を揃えない。** 「一文は40字以内」のような字数ルールを全文に適用すると、全部が同じ長さになる。これがAI臭の最大の発生源で、`scripts/lint.py` の burstiness が検出するのもこれだ。長い文を分割したら、近くに短い断定文を置いて落差を作る。「これは間に合わない。」のような一撃の短文が1つ入るだけで文章は人間のものに近づく。

**段落の文数を揃えない。** 全段落が3〜4文で刻まれているのはAI生成文書の指紋である。1文だけの段落を作ってよい。逆に長い段落があってもよい。均した状態が一番不自然だ。

### 5. 語を置き換える／消す

主要な置換パターンは `references/japanese-patterns.md` にある。文単位の作業に入る前に一度読む。よく効く上位のもの：

| 原文 | 直し |
|---|---|
| 〜することが可能です | 〜できます |
| 〜を実施する／を行う | 動詞1語にする（対応を実施する→対応する） |
| これにより | 削る、または主語を立てて書く |
| 重要なのは〜という点です | 何をすべきかを直接書く |
| 非常に／極めて／しっかりと／きちんと | 削る、または数字に置き換える |
| 〜に関して／〜については | 〜は |
| 〜していく／していきたい | 〜する |
| 〜という形で／〜のような形で | 削る |
| 必要があると考えます | 必要です／〜してください |
| 以下に示します／上記の通り | 削る |
| 課題感／温度感／解像度 | 具体的に何が問題かを書く |

**置換表を機械適用しない。** これは実際に起きた失敗から来ている。この種のlintを作った人が「最後に」「まさに」を禁止語リストから外した理由は、人間もそれらを普通に使うと分かったからだ。表にある語も、文脈で必要なら残る。「削っても意味が変わらないか」を毎回見る。表は疑うべき箇所を教えるだけのもので、禁止語リストではない。

### 6. 表層フォーマットを直す

見た目にもAIの指紋が出る。内容を変えずに直せるので効率がよい。

- 太字の項目名にコロンを付けて説明を続ける箇条書き（`- **項目名**: 説明`）。これが3つ以上並んでいたら、ほぼAI生成である。表にするか、太字を外す。
- 太字の乱用。強調が5箇所以上あると強調として機能しない。読み手が本当に拾うべき1〜3箇所に絞る。
- 見出し直後の内容のない一文。「本節では〜を説明します」は全部削る。
- 見出しが多すぎる。3文しかない節に見出しが付いていたら、上位の節に畳む。
- 絵文字、emダッシュ（—）、タイトルケースの見出し。日本語の業務文書では浮く。emダッシュは読点か括弧に置き換える。
- 箇条書きの粒度不統一。1項目1文のものと3段落あるものが混在していたら、後者は本文に出す。

この節の指摘が自分の出力にも当てはまることに注意する。添削結果の「削ったもの」を太字コロン形式の箇条書きで書いてしまうのはよくある。

### 7. lint を通す

```
python3 scripts/lint.py <ファイル>
```

burstiness（文長のばらつき）、段落の文数の均質性、体言止めの有無、否定対比構文（「〜ではなく」）の出現率、太字コロン箇条書き、ヘッジ・冗長述語・空虚な修飾語の出現数を機械判定する。コードブロック・表・URLは自動で除外される。ブログや読み物なら `--prose` で厳しめの閾値になる。

**検出は「疑い」であって違反ではない。** 全部直すのが正解ではない。直すか、理由をつけて残すかを判断する。特に burstiness と体言止めは、業務文書では無理に動かさなくてよいこともある。判断した内容は「削ったもの」か「確認したいこと」に書く。

lint は添削の前後で2回走らせる。前に走らせるのは当たりを付けるため、後に走らせるのは**自分の添削が均質性を悪化させていないか**を見るためだ。冗長さを削ると文が揃いやすくなるので、burstiness は添削後に悪化しやすい。ここを見ずに出すと「短いけどAIっぽい」で終わる。

### 8. 検算する（省略しない）

圧縮で起きる最悪の事故は、条件付きの記述が無条件になることだ。「本番環境では再起動が必要」が「再起動が必要」になると、読み手は検証環境でも再起動する。原文と添削後を突き合わせて、以下が生き残っているか確認する。

- 固有名詞（サービス名、チーム名、人名、環境名）
- 数字・日付・期限
- 条件節（〜の場合、〜を除き、〜以降）
- 主語（誰がやるのか）
- 否定・例外
- 手順0で決めた「触らない領域」が無傷か

消えているものがあれば戻す。意図的に消したなら「削ったもの」に理由付きで書く。

## 出力の形

前置きを書かず、添削後の本文から始める。「以下のように修正しました」の一行が、まさにこのスキルが消そうとしている種類の文である。

```
## 添削後

（本文のみ）

## 削ったもの

- 「はじめに」節：本論の前提を繰り返していたため
- 各段落末尾のまとめ文（5箇所）：情報がないため
- 「非常に」「しっかりと」等の強調語：削っても意味が変わらないため

## 確認したいこと

- 「関係者と調整の上」の関係者が特定できず、原文のまま残した
- 期限が「早めに」だったため「9/5まで」と仮置きした。要確認

字数: 1,240 → 680（-45%）
lint: 警告9件 → 1件（残1件は burstiness。業務文書として許容と判断）
```

診断だけを求められた場合（「どこが冗長か教えて」）は書き直さず、lintの結果と箇所・理由だけを返す。

## 守ること

**事実を足さない。** 短くする作業で情報が増えるのはおかしい。埋めたくなる空白は「確認したいこと」に回す。

**曖昧さを勝手に確定させない。** 原文が「調整中」なら「調整済み」にしない。読み取れない意図は質問にする。

**声を残す。** 目的は別人が書いたように見せることではなく、書き手が言いたかったことを速く読めるようにすること。原文の語彙を優先し、置換は必要なところだけにする。全文を自分の文体で書き直すと、書き手が自分の文書として出せなくなる。

同じ書き手の他の文章が手元にあるなら（同じリポジトリの別ドキュメント、過去の週報、Slackの投稿）、先に1本読んで**文長の癖、語彙の水準、句読点の打ち方、敬体か常体か**を掴んでから添削する。これをやると「直された感」が出ない。

**文体と丁寧さを勝手に変えない。** 敬体（です・ます）を常体（だ・である）にすると劇的に短くなるので手が伸びるが、これは冗長さの削減ではなく別文書への置換である。読み手や提出先の慣習は書き手しか知らない。原文の文体を維持し、変えたほうがよいと思うなら「確認したいこと」で提案する。社外メールの「ご確認いただけますでしょうか」を「確認して」にはしない。削るのは冗長さで、敬意ではない。ただし社内向けなら「〜させていただく」は「〜する」でよい。

**着地点の目安は3〜5割減。** 半分以下になったときは検算をやり直し、なぜそこまで減ったのかを一行で書く（「はじめに・背景・まとめが原文の4割を占め、固有の情報が無かった」など）。理由が言えるなら6割減でも構わない。言えないなら削りすぎている。逆にほとんど減らないなら、文ではなく構造の重複を見落としている。

**繰り返し指摘される項目を優先する。** 全パターンを毎回等しく適用すると作業が重くなり、効果の薄い直しに時間を使う。同じ書き手の文章を何度か見ていると、その人固有の癖が3〜5個に絞れてくる（ヘッジが多い、まとめ節を必ず付ける、太字が多い、など）。それが分かったら、そこを重点的に見て、残りは lint に任せる。

## 長い文書の扱い

数千字を超えるものは章ごとに処理する。ただし構造の重複（背景とまとめの言い換え）と均質性は全体を通してしか見えないので、まず全文をざっと読んで構造の判断と lint を先に済ませ、そのあと章ごとに文を詰める。

## 英語の場合

同じ原則が効く。特に効くのは、名詞化を動詞に戻すこと（provide support for → support）、"in order to" → "to"、"It is important to note that" の削除、受動態の能動化、"very/really/quite" の削除、emダッシュの多用をやめること、"**Item**: description" 形式の箇条書きをやめること。文長の均質化を避ける点も同じ。

- 16-minds（qiita.com/yukurash）— AI臭の正体を「無味無臭」と捉える見方、「省略する／偏る／具体で殴る」
- japanese-tech-writing / cognitive-rhythm-writing（ai.itokoba.com）— 論理構造の整理とリズムを別の関心事として扱う分離
