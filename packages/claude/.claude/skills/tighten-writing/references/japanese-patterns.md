## 1. AI特有の構文シグネチャ

これらは人間の業務文書にはほとんど現れない。見つけたら文ごと組み替える。

| パターン | 例 | 直し |
|---|---|---|
| 単に〜ではなく、〜だ | 「単にコストの問題ではなく、体験の問題です」 | 言いたい側だけ書く。「体験の問題です」 |
| 〜こそが〜の本質だ | 「この設計こそが可用性の本質です」 | 何がどうなるのか事実で書く |
| 重要なのは〜という点だ | 「重要なのは移行順序という点です」 | 「移行順序を先に決める必要があります」 |
| 三つ並べの乱発 | 「速度、安定性、そして拡張性」 | 3つ全部が必要か確認。1つで足りることが多い |
| 段落末の要約文 | 各段落が「つまり〜ということです」で終わる | 全部削る |
| 呼びかけの締め | 「いかがでしょうか」「ぜひご活用ください」 | 依頼があるなら具体的に書く。なければ削る |
| 見出しごとの予告＋要約 | 節の頭で「本節では〜を説明します」、末で再要約 | 両方削る |
| 対句のリズム | 「〜だけでなく、〜も」が連続する | 片方に寄せる |

## 2. 冗長述語（名詞化の巻き戻し）

日本語のAI文は動作を名詞にして「行う／実施する／を図る／を進める」を足す癖がある。動詞に戻すだけで1割減る。

| 原文 | 直し |
|---|---|
| 対応を実施する | 対応する |
| 検討を進めていく | 検討する |
| 改善を図る | 改善する |
| 確認を行う | 確認する |
| 削減に寄与する | 削減する（数字があれば「20%削減する」） |
| 影響を及ぼす可能性がある | 影響する／（条件を書く） |
| 適用を開始する | 適用する |
| 見直しが必要となる | 見直す |
| 運用を回していく | 運用する |
| 情報の共有を行いたい | 共有します |

## 3. 中身のない修飾語

削っても意味が変わらないなら、それは情報ではない。数字に置き換えられるなら置き換える。

削る候補：非常に／極めて／かなり／大きく／しっかりと／きちんと／適切に／確実に／可能な限り／基本的に／一定の／様々な／多様な／幅広い／柔軟に／スムーズに／円滑に／効率的に

- 「非常に重要な課題」→「（何が起きるかを書く）」
- 「適切に対応する」→ 誰が何をするのか書く。書けないなら未定と書く
- 「可能な限り早く」→「9/5まで」
- 「様々な課題がある」→ 課題を列挙する。列挙できないなら削る

## 4. ヘッジと責任回避

| 原文 | 直し |
|---|---|
| 〜と考えられます | 断定できるなら断定。できないなら「未確認」と根拠 |
| 〜の可能性があると思われます | 〜の可能性があります（重ね掛けをやめる） |
| 〜すべきかもしれません | 〜してください／〜を提案します |
| 必要があると考えます | 必要です |
| 認識しています | （多くの場合削れる） |
| 〜と言えるでしょう | 削る |
| 〜ではないでしょうか | 主張として書く |
| 〜ないわけではない | 肯定形にする |

判断を避けた文は読み手に判断を丸投げしている。書き手の立場を1文で出すほうが短く、役に立つ。

## 5. 前置き・後置きの定型句

ほぼ全部削れる。

削る候補：本ドキュメントでは／以下に示します／以下の通りです／上記の通り／前提として／結論から言うと／まず初めに／なお／ちなみに／念のため／参考までに／簡単に説明すると／詳細は後述しますが

- 「結論から言うと」は不要。結論を先に書けば読み手に伝わる。
- 「以下に示します」の直後に表や箇条書きが来るなら、見れば分かる。
- 「なお」で始まる文は、本文に統合できるか、削れるかのどちらかが多い。

## 6. 接続詞と転換フレーズ

段落の頭に接続詞が並ぶのはAI文の指紋。半分以上削れる。

- また／さらに／加えて → 並列なら箇条書きにする
- そのため／したがって／よって → 因果が自明なら削る
- 一方で／他方 → 対比が本当にあるときだけ
- このように → ほぼ常に削れる
- つまり／すなわち → 前の文が分かりにくいのが原因。前の文を直す

## 7. 抽象カタカナ語と社内ジャーゴン

具体語に戻す。戻せないなら、書き手も何を言っているか決めていない。

| 原文 | 直し |
|---|---|
| シナジー | 何と何がどう繋がるのか |
| アラインする | 合意する／揃える |
| ドライブする | 進める／主導する |
| コミットする | 約束する／期限を書く |
| 課題感がある | 何が問題か書く |
| 温度感 | 優先度／緊急度／賛否 |
| 解像度が低い | 具体性がない／未検討 |
| 目線を合わせる | 前提を共有する |
| ケイパビリティ | できること／機能 |
| ワークする | 機能する／うまくいく |
| 巻き取る | 引き受ける |

## 8. 英語直訳臭

| 原文 | 直し |
|---|---|
| 〜することが可能です | 〜できます |
| 〜する必要性がある | 〜が必要です |
| 〜という事実がある | 〜です |
| 〜に関して／〜については | 〜は |
| 〜において | 〜で |
| 〜を通じて | 〜で |
| 〜に基づいて | 〜から／〜をもとに |
| 〜における課題 | 〜の課題 |
| 〜のような形で | 削る |
| 〜という点において | 削る |

受動態も同じ。「対応が行われる」→「（誰が）対応する」。主語が書けないと気づいたら、それは埋めるべき情報の穴である。

## 9. 構造レベルの重複

文単位より効果が大きい。全文を通してしか見えないので、章ごとの作業に入る前に判定する。

| 重複 | 直し |
|---|---|
| 背景 ≒ 本論の前半 | 読み手が既に知っていることは削る。判断に必要な前提だけ残す |
| まとめ ≒ 本論の言い換え | 削る。決定事項・ToDo・未決事項のような新しい情報だけ残す |
| 節の予告と節の要約 | 両方削る |
| 表と散文の二重説明 | 表を残し、散文は表から読み取れないことだけ書く |
| 箇条書きの後の解説文 | 箇条書きに情報を吸収させる |
| 同じ懸念が複数節に散っている | 1箇所にまとめる |

## 10. 箇条書きの直し方

- 粒度を揃える。1項目が1文で済むものと3段落あるものが混在していたら、後者は本文に出す。
- 各項目を体言止めか文かで統一する。
- 項目の頭に「〜については」を付けない。
- 項目が7つを超えたらグループ化を検討する。
- 「その他」は中身を書くか削る。
- ToDoの箇条書きには必ず「誰が」「いつまでに」を入れる。入れられないなら、それは検討事項であってToDoではない。

## 11. 均質性 — 削っても消えないAI臭

冗長さとは別系統の問題である。ここを見落とすと「短いのにAIっぽい」文章になる。`scripts/lint.py` が数値で出すのはこの節の項目。

### 文長が揃っている（burstiness）

AIは似た長さの文を並べる。人間は長い説明のあとに「無理だ。」と置く。指標は
`burstiness = (標準偏差 − 平均) / (標準偏差 + 平均)` で、0に近いほどばらつきがある。
読み物では −0.24、業務文書では −0.35 を下回ったら疑う。

添削でこれは**悪化しやすい**。長い文を分割して全部を中くらいの長さに揃えるからだ。分割したら、近くに短い一撃を置いて落差を作る。

- 悪化例：「現行実装は2021年のもので、当時の想定を超えるトラフィックになっている。決済手段も増え、実装の複雑性が上がっている。個別対応ではなく設計の見直しが必要になっている。」（全部45字前後）
- 直し：「現行実装は2021年のままだ。当時の想定を超えるトラフィックに加え、決済手段も増えて実装が複雑化している。個別対応では追いつかない。」（22字／48字／16字）

### 段落の文数が揃っている

全段落がきっちり3〜4文で刻まれているのはAI生成の指紋。1文だけの段落を作ってよい。段落文数の変動係数が 0.194 以下なら疑う。

### 体言止めがゼロ

全文が「です」「ます」「である」で終わると機械的に読める。見出しや箇条書きだけでも体言止めを混ぜると変わる。ただし業務文書で本文に無理に入れる必要はない。

### 「〜ではなく」「〜だけでなく」の反復

否定と肯定を対比させる構文はAIが好む。人間の使用率は文数比で1.5%程度、AIは8.3%程度と報告されている。言いたい側だけ書けば足りることが多い。

### 敬語のレベルが全文で一定

人間は重要な依頼だけ丁寧度を上げ、事実の列挙は素で書く。全文が同じ丁寧度で塗られていると平坦になる。ただし文体そのもの（敬体／常体）を変えるのは別問題で、これは勝手に変えてはいけない。

## 12. 表層フォーマットの指紋

内容を変えずに直せるので効率がよい。

| パターン | 直し |
|---|---|
| `- **項目名**: 説明` 形式の箇条書きが3つ以上 | 表にする、または太字を外す |
| 太字が5箇所以上 | 1〜3箇所に絞る。全部太字は全部普通と同じ |
| 見出し直後の「本節では〜を説明します」 | 削る |
| 3文しかない節に見出し | 上位の節に畳む |
| 絵文字 | 業務文書では削る |
| emダッシュ（—） | 読点か括弧に |
| 箇条書きの粒度不統一（1文と3段落が混在） | 長いものは本文に出す |
| 「まとめ」「おわりに」「今後の展望」の定型セクション | 新しい情報がなければ削る |

## 13. 無味無臭（正論・両論併記・過剰な親切さ）

冗長さがなくても読む価値がない文章がある。AI臭のもう一つの成分。

正論だけで固有名詞と数字がない。「読者目線で」「結論ファーストで」のような、誰も反対しないことだけが書かれている段落は、固有名詞・数字・具体的な場面に置き換える。

両論併記。「〜という意見もあれば、〜という意見もある」で終わっている箇所には書き手の判断がない。立場を出すか、「未決」と明記する。並べただけが一番読み手を止める。

過剰な親切さ。読み手が知っている用語の定義から入る、段落ごとに要約を付ける、接続詞で毎回つなぐ。読み手を信用していない文章は長くなる。

曖昧な出典。「一般的に言われている」「多くの企業では」。出典を書くか、削るか、「未確認」と書く。

意味のない範囲表現。「3〜5個程度」「数週間程度」。決まっているなら数字を、決まっていないなら「未定」を書く。

名前の羅列。有名なサービス名や手法名を並べて説明した気になっている箇所。自分の文脈でどう使うのかを書く。

## 14. このリストを機械適用しないこと

このファイルは禁止語リストではない。疑うべき箇所を教えるだけのものである。

実例がある。同種のAI臭lintを作った人は、当初「最後に」「まさに」を禁止語に入れていたが、人間の文章での使用が多いと分かって削除した。文脈で必要なら残るのが正しい。

判定の基準は常に一つ、**削っても意味が変わらないか**。変わらなければ削る。変わるなら残す。カウントが閾値を超えたから直す、ではない。

lintの検出も同じ扱いで、直すか、理由をつけて残すかを毎回判断する。判断した内容は添削結果の「削ったもの」か「確認したいこと」に書き残す。そうしないと書き手が検証できない。
