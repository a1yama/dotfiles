## 何を防ぐスキルか

長時間の作業では、途中で採った評価軸が固定化し、他の目的が視野から消える。実際に起きた例:

> 全部を「モデルの精度が上がるか」で判断していた。学習に使えないデータを、判断材料としての価値ごと捨てていた。自前DBに58,124走ぶんのデータが最初から入っていたのに「何が計算できるか」を一度も考えず、パイプラインの修理に没頭していた。設計エージェントの助言も書き留めただけで実行しなかった。

**自分のコンテキストの中では、自分の枠組みは正しく見える。** だから採点者を自分以外にする。

## 手順

### 1. ブリーフを組み立てる

以下を埋める。**ユーザーの依頼文は原文をそのまま引用する。** 要約・言い換えは自分の枠組みで汚染されるため禁止。

- このタスクの発端になったユーザーの発言(原文引用)
- いま最適化している指標・評価軸(自分の言葉で1行)
- 直近の作業内容 — 何を触り、何を後回しにしたか(`.claude/notes/<task>.md` があればパスを渡して参照させる)
- 「使えない」と判断して捨てた選択肢・データの一覧
- 未実行の提案 — 他エージェント・ユーザー・過去の自分のもの
- 手持ちの資産 — 既存のデータ・コード・成果物

**捨てたものと未実行の提案を「なし」で埋めない。** 思い出せないなら「思い出せない」と書いて notes と git log のパスを渡す。空欄で出すと監査が成立しない。

### 2. 監査させる

Agent ツールで `subagent_type: frame-review-fable` に上記ブリーフを渡す。1リクエストで全部渡す(小出しにしない)。

### 3. 指摘を処理する

**「認識しました」と記録するだけで流すのは禁止。** これが防ごうとしている失敗そのもの。指摘ごとに次のいずれかに落とす。

- **実行** — このターンで着手する
- **タスク化** — `TaskCreate`(無いセッションでは `TodoWrite`)で登録し、`.claude/notes/` にも残す。
  **ツールが見つからないことを理由に notes へ書くだけで済ませない。** それがこのスキルの防ごうとしている「記録止まり」そのもの。書いた上で `次の一手` に載せる
- **棄却** — 理由を1行、最終報告に残す
- **方針転換の判断が要る** — AskUserQuestion でユーザーに出す

### 4. 報告する

最終報告の**既存の節**に流す。専用の節は作らない。

- 問題なし → `検証` に1行(例: `frame-check → 問題なし`)
- 要修正 → 指摘と処理を `未達` または `次の一手` に反映する
