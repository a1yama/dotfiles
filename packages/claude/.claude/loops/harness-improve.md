# ハーネス改善ループの手順

無人の定時実行(`claude-loop` の `harness-improve`)がこの手順を1周だけ行う。
対象はこのリポジトリの Claude 用ハーネス(`packages/claude/` のフック・規約・スキル・チェックリスト・補助コマンド)。

## 目的と完了条件

- 目的: 実際の作業で起きた「止められた」「やり直した」「食い違っていた」を、次から起きないようにする。
- 1周で直すのは**最大1件**。直す根拠が弱い日は**何も変えずに終わる**のが正しい結果。変更を出すこと自体を目的にしない。
- 完了条件(どれか1つ):
  - 1件を直し、`harness-gate` が exit 0、ローカルのブランチに commit 済み、報告を書いた。
  - 直す対象が無い、または下の停止条件に当たり、理由を報告に書いた。

## やってはいけないこと

- **`git push`、PR の作成、master への直接 commit。** このリポジトリは公開されている。push は所有者が対話セッションで確認してから行う
  (`claude-loop` 側で push は失敗するようにしてあるが、別の経路を探さない)。
- **`settings.json` 系のファイルを変える。** マシンごとの値が入っており、stow でも同期していない。
- **安全装置を変える。** `harness-gate`、`claude-loop`、その2つのテスト、この手順書、`.config/claude-loop/` の設定。
  直す必要があると考えたら、実装せず報告の「提案」に書く(対話セッションでだけ変える)。
- **GitHub へ書き込む別の経路を使う。** `gh`、GitHub の API、MCP。push が失敗するのは設定どおりの動作で、回避する対象ではない。
- **`packages/claude/` の外を変える。**
- **検査を緩める方向の変更。** フックの判定を外す・弱める、テストの期待値を合わせにいく、確認なしでよい範囲を広げる、
  `CLAUDE.md` の「本人指示」と書かれた決まりを書き換える。必要だと考えたら、実装せず報告の「提案」に書く。
- **会話の中身をリポジトリに書く。** 会話ログは手がかりを探すために読むが、作業名・リポジトリ名・人名・社名・パス・URL・
  発言の引用をコード・コメント・テスト・文書・コミットメッセージに書かない。一般化した構造だけを書く。
- **実際の `claude` を起動するテストを足す。** テストは必ず偽の `claude` を PATH に置いた形にする。

## 手順

### 0. 停止条件を先に確かめる

```bash
git branch --list 'loop-harness-improve/*' --no-merged origin/master
```

- 未反映のブランチが **3本以上**あれば、新しい変更は作らない。所有者の確認待ちが溜まっている。本数を報告に書いて終わる。
- 未反映のブランチがあれば、それぞれが何を直したかを `git log` で読む。同じ題材を重ねて直さない。

### 1. 手がかりを集める

1. 会話ログの集計: `packages/claude/.local/bin/harness-signals --days 7`
   - `hook_denials`: フックが止めた操作。件数と、出たセッション数。
   - `tool_exceptions`: `# tool-exception:` を付けて通したコマンド。多いものは、自動で許可すべき形の候補。
   - `rework`: 所有者が手戻りを指摘した発言の場所。前後を読み、同じ種類の失敗が2回以上あるかを見る。
     語の一致で拾っているだけなので、読んで手戻りでなければ数えない。
2. テスト: `packages/claude/.claude/hooks/tests/` の `*.test.sh` を全部実行する。
3. 文書と実体の食い違い: `CLAUDE.md`・`README.md`・各 `SKILL.md` が名前を挙げているファイル・コマンド・フックが実在するか、
   書いてある挙動と実装が合っているかを確かめる。
4. スキルの使用実績: 同じ `harness-signals` の出力にある。
   - `skill_usage`: 直近60日の使用回数と最後に使った日。
   - `skills_unused`: 定義されているのに60日間一度も使われていないスキル。
   - `skills_too_new`: 期間より後に作られたスキル。使われていなくて当然なので、削除の対象にしない。
   - `sessions_scanned`: 数えた会話の数。**20 未満なら、使われていないことは削除の根拠にならない**(対話そのものが少ない)。
     その場合、未使用スキルは発火の実測と説明文の改善までにして、削除はしない。
   - 見えるのはこのマシンの会話ログだけ。他のマシンでの使用は数えられていない。

### 2. 直す1件を選ぶ

上から順に見て、最初に条件を満たしたものを選ぶ。どれも満たさなければ、何も変えずに 5 へ進む。

| 優先 | 手がかり | 選ぶ条件 |
|---|---|---|
| 1 | 落ちているテスト | 1本でも落ちている |
| 2 | フックの拒否 | 同じ種類が 3回以上、かつ 2セッション以上。誤って止めている、または案内が役に立っていない |
| 3 | 手戻りの発言 | 同じ種類の失敗が 2回以上あり、規約かフックで防げる |
| 4 | `# tool-exception:` の多用 | 同じコマンドが 10回以上。専用ツールで代替できない使い方が、自動で許可されていない |
| 5 | 文書と実体の食い違い | 存在しないものへの参照、または実装と違う記述 |
| 6 | スキルの手入れ | 下の「スキルの手入れ」の条件を満たすものがある |

フックの拒否は「正しく止めた」ものが大半になる。件数が多いだけでは直す理由にならない。
直すのは、止める必要が無かったもの(誤検知)か、止めた後の案内どおりにしても進めなかったものに限る。

`# tool-exception:` の多用を直すと、たいていフックの許可を広げることになる。それは「検査を緩める方向」なので、
実装せず、件数と許可すべき形を報告の「提案」に書く。実装してよいのは、案内の文面や順序の改善のように、止める範囲を変えないものだけ。

### スキルの手入れ(優先 6 の中身)

1周で扱うスキルは1つ。発火の実測(`skill-trigger-eval` スキル)は `claude -p` を何本も起動するので、**1周に1スキルまで**。
前回どのスキルを見たかは記録ファイルにあるので、同じスキルを7日以内に測り直さない。次の順で1つ選ぶ。

1. **使われていないスキル**(`skills_unused` のうち、`packages/claude/.claude/loops/skill-keep.txt` に無いもの)
   - まず発火を実測する。使われていない理由が「要らない」のか「呼ばれるべき場面で発火していない」のかは、使用回数からは分からない。
   - 発火すべき依頼の半分以上を取りこぼしている → **説明文(description)を直す**。直した後にもう一度測り、良くなっていなければ変更を捨てる。
   - 発火するのに使われていない → **削除する**。スキルのディレクトリごと消し、`README.md` や他のスキル・規約からの参照も一緒に直す。
     削除は1周に1つまで。記録に `"signal": "skill_removed"` と、実測の結果、このマシンでの使用回数(0回・60日)を書く。
   - 削除が正しいかは、このマシンの実績だけでは決まらない。所有者が push を確認するときに、他のマシンでの使用回数と突き合わせる。
     報告に「削除: <スキル名>。このマシンで60日間 0回、実測では発火した」と書く。
2. **使っているスキルの改善**(`skill_usage` の上位)
   - そのスキルを使った直後に手戻りの発言がある会話を読む。同じ種類の取りこぼしが 2回以上あれば、スキルの手順に足す。
   - 別のスキルに横取りされている、または関係ない依頼で発火している、と実測で分かったら説明文を直す。
   - 根拠が無いのに文面を整えるだけの変更はしない。
3. **新しいスキルの作成**
   - 条件: 同じ手順を人が指示し直している、または同じ手作業の列が 3回以上・2セッション以上で繰り返されていて、既存のスキルに該当するものが無い。
   - 特定のリポジトリの中だけで使う手順は、ここには作らない(そのリポジトリの手順書に置くものなので、報告の「提案」に書く)。
   - 作ったら発火を実測し、発火すべき依頼の半分以上で発火することを確かめてから commit する。届かなければ変更を捨てる。
   - 会話に出てきた固有名・作業の中身を、スキルの本文や例に書かない。

### 3. 直す

- 先に原因を特定する。症状に合わせた個別の例外を足さない。
- 変更の前に、再発を捕まえるテストを書く。フックの変更は `tests/<フック名>.test.sh` に足す。
- 変更は小さく保つ。1件に関係しない整理や書き換えをしない。

### 4. 検査してから commit する

```bash
gate=$(mktemp) && git show origin/master:packages/claude/.local/bin/harness-gate > "$gate" && [ -s "$gate" ] && python3 "$gate" --base origin/master
```

**必ず1行でつないで実行する。** 取り出しに失敗したまま次の行で実行すると、空のファイルが動いて exit 0 になり、検査なしで通ってしまう。
検査には **origin/master 側の版**を使う。作業ツリーの版を使うと、変更した検査で自分の変更を検査することになる。

- **exit 0 以外では commit しない。** 指摘を直して再実行する。3回直しても通らなければ、変更を捨てて(`git checkout -- . && git clean -fd`)
  理由を報告に書く。
- 検査を通すために検査側を変えない。変更が大きすぎる(追加 300 行超)と言われたら、分けずに範囲を絞る。
- 通ったら、ブランチを切って commit する。push はしない。ブランチ名の接頭辞は変えない(`claude-loop` が確認待ちの本数を数えて所有者に通知する)。
- ブランチ名とコミットメッセージにも会話の中身を書かない。題は「どのフックの何を直したか」だけにする。
- ブランチを切った後にもう一度、同じ検査を実行する(ブランチ名とコミットメッセージも検査される)。

```bash
git checkout -b "loop-harness-improve/$(date +%Y%m%d)-<英小文字とハイフンの短い題>"
git add packages/claude
git commit -m "update"
```

### 5. 報告と記録を書く(リポジトリの外)

会話の中身に触れるので、どちらも**リポジトリの外**に置く。

- 報告: `~/.local/state/claude-loop/reports/harness-improve/<YYYY-MM-DD>.md`
  - 手がかりの件数(拒否の上位、例外の上位、手戻りの件数、落ちたテスト、食い違い)
  - 選んだ1件と、選んだ根拠(件数)。選ばなかったなら、どの条件にも届かなかったこと
  - 変えたファイル、`harness-gate` の結果、ブランチ名
  - 提案(検査を緩める方向など、実装しなかったもの)
  - 未反映のブランチの一覧
- 記録: `~/.local/state/claude-loop/harness-improve.ledger.jsonl` に1行追記する。
  - `{"date": "...", "branch": "...", "signal": "<手がかりの種類>", "key": "<拒否の種類など>", "count_before": <件数>}`
  - スキルを実測した日は `{"date": "...", "skill_checked": "<スキル名>", "result": "<発火した割合>"}` も追記する。

### 6. 前に直したものが効いたかを確かめる

反映は、所有者が対話セッションでブランチを master に merge(fast-forward か merge コミット)して push する形で行われる。
squash や rebase で取り込まれると `--merged` に出ず、未反映のまま数えられる。その場合は報告に書く。

記録のうち、commit から7日以上たち、master に反映済み(`git branch --merged origin/master` に出る)のものについて、
同じ `key` の今の件数を数える。減っていなければ「効いていない」と報告に書く。直し方が原因に当たっていなかった可能性が高い。
効いていないものが出たら、次の周で優先 2 より上に置いて原因から見直す。

最後に、報告の要点(直した1件、ブランチ名、所有者に確認してほしいこと)を最終応答として出す。
